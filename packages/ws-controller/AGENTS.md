# ws-controller — non-obvious invariants

- **Typed state vs. attribute cache.** Wire serialisation (`AttributeDataCache.ts`) reads the attribute cache and flattens struct fields to numeric-tag-keyed objects for the Python-compatible protocol. Decision logic — anything that branches on a device's current state, such as `packages/ws-controller/src/camera/` — reads `endpoint.stateOf(XxxClient)` instead. The cache's flattening is lossy: a mis-keyed lookup returns `undefined` rather than a type error, and a default can then silently stand in for real device data (issue #1054). `stateOf` gives typed fields, so the same mistake is a compile error instead of a silent wrong answer. Do not add cache reads to new decision code; if a subsystem needs both (serving state over the wire and deciding on it), read `stateOf` once and serialise from that, rather than reading the cache a second time for the same fact.
- **SDP `a=fmtp` limits are per payload type, never per offer.** `sdpConstraints.ts` keys them by codec, and `videoCodecLimits(sdp, codec)` reads them out tagged with that codec. Do not reintroduce a flat `maxPixels` / `maxBitRate` on the offer: browsers offer H.264 and H.265 with different level caps, and one folded ceiling clamps the selected codec to the other codec's limit. `max-fs`, `max-mbps`, `max-fr` and `max-br` are parsed. Note what is *not*: `profile-level-id` (H.264), `level-id` and `max-fps` (H.265), which is where a peer usually states its real ceiling, so a codec offering only a level is unconstrained here. Reading a level means mapping it onto the per-level luma picture size and sample rate tables, which is a table with its own correctness surface and no hardware here to check it against.
- **The offer's limits are a decode ceiling, not a preference.** They live in `VideoCallerBounds`, so `satisfiesVideoCallerBounds` applies them and every rung that hands a stream out — reuse, make-room, degraded — is bound by them. A rung may give up the envelope the server computed; video the peer cannot decode is not a degraded picture, it is no picture. `offerFrameRateCeiling` is shared by the envelope and the gate so the rate the server allocates at and the rate it accepts a candidate at cannot drift apart.
- **`MediaDisposition` has three values because a refusal is not an absence, and its codec list has two meanings.** An `m=` section with port 0 is the peer declining that media kind; no section at all leaves the decision to the server. The parser used to read a rejected section as if the peer had offered it — its codecs narrowed the selection, its `a=fmtp` limits clamped the envelope, a rejected audio section could set `wantsTalkback`, and a stream was allocated and attached to the answer for it. Dropping the section instead is not the fix either: an offered section carrying only statically-mapped payload types states nothing about what the peer decodes, and narrowing by that empty statement is what refused a caller for a codec mismatch nobody stated. So `offered` carries its codec list only when the peer stated one, `offeredCodecs()` is the single read path for both kinds, and refusal is answered where the track is decided, ahead of any narrowing.
- **A track request has three states and one answer site.** `trackRequest(args.video)` reads the wire argument as `declined` (`false`), `deferred` (key absent) or `demanded` (key present, `{}` included). The resolvers never throw an absence: they return a `TrackOutcome`, and `CameraStreamManager.resolveTrack` is the only place that turns "no stream" into either a null track or the typed failure. Do not let a resolver decide that itself — video and audio answering the question in their own places is what produced a session with `video: null` and no error for a caller that had stated video bounds. What still differs is which outcomes reach `resolveTrack` at all: the audio resolver reports every dead end as `unavailable`, the video one reports only the offer's refusal and throws for the rest, because a camera refusing video is a failed session rather than an audio-only one.
- **The offer's direction is read for talkback only.** A video section with `a=inactive` or `a=sendonly` still counts as offered, so a stream is allocated for a peer that will not receive it, and an offer with no video section at all allocates video although `ProvideOffer`'s answer cannot add the m-line. Both are open; do not assume the disposition already covers them.
- **Open, recorded here because the notes they came from are not committed:** the two direction cases above; codec choice takes `candidates[0]` from the device's or the caller's order and never the offer's m-line preference order, which now also decides whose `a=fmtp` limits apply; an `a=fmtp` line whose payload type has no `a=rtpmap` is dropped; and capacity decisions read `referenceCount` from a subscription-backed cache the session registry could answer more accurately.
