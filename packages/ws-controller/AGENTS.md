# ws-controller — non-obvious invariants

- **Typed state vs. attribute cache.** Wire serialisation (`AttributeDataCache.ts`) reads the attribute cache and flattens struct fields to numeric-tag-keyed objects for the Python-compatible protocol. Decision logic — anything that branches on a device's current state, such as `packages/ws-controller/src/camera/` — reads `endpoint.stateOf(XxxClient)` instead. The cache's flattening is lossy: a mis-keyed lookup returns `undefined` rather than a type error, and a default can then silently stand in for real device data (issue #1054). `stateOf` gives typed fields, so the same mistake is a compile error instead of a silent wrong answer. Do not add cache reads to new decision code; if a subsystem needs both (serving state over the wire and deciding on it), read `stateOf` once and serialise from that, rather than reading the cache a second time for the same fact.
- **SDP `a=fmtp` limits are per payload type, never per offer.** `sdpConstraints.ts` keys them by codec, and `videoCodecLimits(sdp, codec)` reads them out tagged with that codec. Do not reintroduce a flat `maxPixels` / `maxBitRate` on the offer: browsers offer H.264 and H.265 with different level caps, and one folded ceiling clamps the selected codec to the other codec's limit. `max-fs`, `max-mbps`, `max-fr`, `max-br`, H.265's `max-fps` (frames per 100 seconds, RFC 7798 §7.1) and the codec's own level are all parsed. The level is where a peer usually states its real ceiling, so treating it as no statement made a level-only offer unconstrained, which is the opposite of the rule this subsystem is built on. `codecLevels.ts` holds the two tables — ITU-T H.264 Table A-1 (MaxFS, MaxMBPS, MaxBR) and ITU-T H.265 Table A.8 (MaxLumaPs) with Table A.9 (MaxLumaSr) — and each cites the table it came from, because no Matter model states them. Four things are easy to get wrong and are decided in one place each: `profile-level-id` is three bytes and only the last is the level; level 1b has two spellings, `level_idc` 9 and `level_idc` 11 with `constraint_set3_flag` set on profile 66, 77 or 88 (H.264 §A.3.1, RFC 6184 §8.1), and the second spelling is level 1.1 on every other profile; an explicit capability parameter overrides the level's value rather than tightening against it, because both payload formats define such a parameter as signalling a capability at or above the level's; and the parameter names are per codec and never shared. `FMTP_PARAMETERS` in `sdpConstraints.ts` is where the second point lives: H.264 states `max-fs` / `max-mbps` in macroblocks and `max-fr` in frames per second (RFC 6184 §8.1, RFC 7741 §6.1), H.265 states `max-lps` / `max-lsr` in luma samples and `max-fps` in frames per 100 seconds (RFC 7798 §7.1), and `max-br` is units of 1000 bits per second in both. Reading H.264's `max-fs` on an H.265 record let a token H.265 does not define lift the ceiling `level-id` had stated. A codec with no entry falls back to H.264's names and units, because that is what every earlier release read for every codec and removing it would widen a bound an offer already states. H.264's MaxBR is taken at the `cpbBrVclFactor` of the Baseline / Main / Extended profiles — the High profiles scale it by 1.25, so the unscaled number is the tighter bound and errs in the safe direction — and no bit rate is derived from an H.265 level at all, because H.265 states MaxBR per tier and a guessed tier is not a bound. A ceiling this server cannot read is not treated as absent: the codec goes into `unreadableCeilingCodecs`, `decodableVideoCodecs` is the one read path that splits it out, and `preferredVideoCodec` refuses with `reason: "level"` when that leaves nothing. Two things reach that set, and a capability parameter is the second: `fmtpNumber` answers `absent`, `read` or `unreadable`, and a value that is not whole digits — `max-fs=8160px` — makes the codec unselectable rather than falling back to the level. Falling back is what the parameter's own semantics forbid, since it overrides the level rather than tightening against it, so the level is no longer a ceiling the peer states; and with no level stated beside it the codec came out unbounded, which is the one direction a decode bound may not move. Reading a digit prefix instead answers with a number the peer did not state. The set is keyed by codec name, so one unreadable record makes the codec unselectable for the whole session even where another payload type of the same codec states a readable ceiling — which is what the level case already did, and the safe direction: the peer stated something about that codec this server cannot hold it to. `reason: "level"` therefore means "a decode ceiling this server cannot read", which is what the documents describing it now say. The codec is *not* dropped from the section's codec list, because a list narrowed to empty reads as "the peer stated no codec", which is the unconstrained statement. What is still not applied is the RFC-inferred default for an absent level (H.264 `42000A`, H.265 `level-id` 93): H.264's is Baseline level 1, whose MaxMBPS bounds 1080p below one frame per second, so inferring it from a record stating only `max-fs` would refuse offers no peer meant to restrict.
- **The offer's limits are a decode ceiling, not a preference.** They live in `VideoCallerBounds`, so `satisfiesVideoCallerBounds` applies them and every rung that hands a stream out — reuse, make-room, degraded — is bound by them. A rung may give up the envelope the server computed; video the peer cannot decode is not a degraded picture, it is no picture. `offerFrameRateCeiling` is shared by the envelope and the gate so the rate the server allocates at and the rate it accepts a candidate at cannot drift apart, and it may answer 0: rounding it up to 1 widened the peer's stated pixel rate at a resolution it cannot decode at any rate. `computeVideoEnvelope` spends the pixel-rate budget on frame size before reading the rate, since a stream runs at one frame per second at the least, so the rate it allocates at is never 0.
- **The camera's encoder budget is read, not discovered through a refusal.** `budgetVideoEnvelope` narrows the envelope's ceilings into `MaxEncodedPixelRate` (§11.2.7.2) minus what the camera's own streams reserve. **The cluster states no per-stream formula** — §11.2.6.9.4 states one for a snapshot *capability* only — so the sum is the reference server's own, copied from `CameraAVStreamManagementCluster.cpp`'s `IsResourceAvailableForStreamAllocation`: `maxFrameRate × maxResolution` over every allocated video stream, plus `frameRate × maxResolution` over every snapshot stream whose `EncodedPixels` is set (§11.2.6.13.8), which is why `AllocatedSnapshotStream` carries `frameRate` and `encodedPixels`. Cite that function, not a spec section, when this arithmetic is questioned. Note also that the same reference function counts **every** allocated video stream against `MaxConcurrentEncoders`, while `encodersExhausted` counts only referenced ones — a deliberate, separate divergence documented there. It moves **ceilings only**: the envelope's floors already carry every floor the caller stated, so a caller whose bound needs more than the budget has left reaches the device unshrunk and the camera arbitrates (§11.2.1.2.2). That is what makes the branch-free `clampUp(..., envelope.minResolution)` and `Math.max(envelope.minFrameRate, ...)` correct rather than lenient — do not replace them with a test against the caller's hints, which would state the same rule twice. The `undefined` guard is not cosmetic and must not be folded into the `free <= 0` test: `undefined - committed` is `NaN`, `NaN <= 0` is **false**, and the function would then send `maxResolution: {NaN, NaN}` and `maxFrameRate: NaN` to the device. The two do reach the same *outcome* — narrow nothing — by different routes, and only the guard reaches it safely. The budget spends the frame rate before the frame size: `scaleToPixels` only shrinks the frame when even one frame per second at full size does not fit, and the rate is what absorbs the rest. That can leave a `LiveView` envelope at full sensor size and `maxFrameRate: 1` when the free budget sits between one and two sensor frames. It is not flagged `degraded` — that flag is about an *existing* stream outside the envelope, while here the stream fits an envelope that was itself narrowed — so the narrowing has its own report: `budgetVideoEnvelope` answers `{ envelope, narrowed? }`, `narrowed` naming the ceilings that moved and carrying the value each had before, and the ladder attaches it to the allocate path's `ResolvedStream.budgetNarrowed` (`video.narrowed_by_encoder_budget` on the wire). Derive `narrowed` from the two ceilings this function computed, never from whether a budget was applied: a caller floor that clamped a ceiling back up has cost the caller nothing and must not be reported. It is attached on the allocate path only, because a reused or degraded stream carries the camera's own range. Preferring motion over size instead would need a frame-rate target this server has no authority to pick — the dashboard's hardcoded 30 is exactly the "bound nobody asked for" this branch refuses — and §11.2.1.2.2 states the opposite preference for the camera ("SHOULD utilize the highest resolution and bitrate the network can support"). A caller that wants motion states `min_frame_rate`, which the budget may not narrow past, and `frame_rate.max` in the response reports what it got. **Reuse is deliberately outside all of this**: `findReusableVideoStream` gets `selection.envelope`, never the budgeted one, because a stream the camera already produces is already spending the budget and measuring it against what is left turns a free answer into an allocate.
- **The video ladder narrows before it evicts, and re-derives the envelope after it does.** Giving up range costs nobody anything; `VideoStreamDeallocate` costs the victim's holder an id the camera then forgets, and §11.2.1.1 asks commissioners to pre-allocate long-lived streams, so an idle stream is usually a reservation rather than waste. The narrowing budget is therefore spent before `freeAnUnreferencedVideoStream` is reached, and it is **not** refilled by an eviction — a camera that refused every narrowing has said a smaller request is not what it lacks. After an eviction the envelope comes from `budgeted(liveStreams, liveSnapshotStreams)` again rather than from where narrowing left it: the facts it was computed from changed, and paying for capacity without using it costs the caller picture size for nothing. Termination does not rest on `MAX_ALLOCATE_ATTEMPTS`: narrowing has its own budget and the victim set strictly shrinks, since a freed stream is filtered out of `liveStreams`. `DynamicConstraintError` still never reaches the eviction rung — only `ResourceExhausted` does — so round 1's status meanings are intact.
- **The make-room rung takes this server's own snapshot stream before anything of anyone else's, and only one whose loss buys something.** It is the first half of the one order rule stated on `chooseEvictionVictim`. `freeOwnSnapshotStream` runs ahead of `freeAnUnreferencedVideoStream` and offers `chooseSnapshotStreamToFree` only the streams `ownsSnapshotStream` claims — the lease's own allocation record has to match what the camera reports, because a camera reissues a freed id and a never-confirmed lease lives for the process run, so an id match alone can name another controller's stream. `referenceCount === 0` is what `SnapshotStreamDeallocate` refuses on (§11.2.8.10.2; the reference server has no `Internal` case for snapshots), and `CaptureSnapshot` does not raise that count, so a stream this server polls reads 0: unreferenced is not unused, which is exactly why only our own are eligible. A candidate also has to free capacity *this* camera states — an encoder (§11.2.6.13.9), or a share of `MaxEncodedPixelRate` (§11.2.6.13.8) on a camera that states one, since `budgetVideoEnvelope` is the identity without it and the retry would repeat the request that just failed. Encoder holders go first, then size: `MaxConcurrentEncoders` is one on the hardware this rung exists for, and a capacity refusal states nothing about which limit it hit. It comes before the video rung because the camera's `StreamUsagePriorities` ranks video usages and says nothing about snapshot streams, so there is no ranking to fold it into. The freeing registers a restore with the allocation scope, like the video rung's and for its reason. Do not let it run when `allowEviction` is false, and do not put the id in `ResolvedStream.evicted`, which is video stream ids. The ladder keeps its own copy of the snapshot list — seeded with the unreported ones — so the re-derived envelope and the exhaustion report both describe what the camera has after the eviction, not before.
- **A stream the make-room rung took is announced to everyone, not only to the request it served.** `events.streamEvicted` is emitted where the deallocate succeeds, so the client holding an id that stopped existing can learn it; `camera_start_stream`'s `video.evicted_stream_ids` tells the caller that benefited, and carries video stream ids only — a snapshot id belongs in the event alone, which is why the event states its `kind`. Do not emit it from `#deallocate` or `releaseStream`: those give back what this server took or what a client asked to release, and neither destroys anything on another client's behalf.
- **Every camera event goes out through `#announce`, never `emit` directly.** matter.js's `Observable.emit` rethrows an observer's error and hands back the promise of an observer that answers with one, so a bare `emit` lets a listener fail a `camera_stop_stream` that already ended the session on the camera, abort a shutdown pass, skip the replacement registration that follows an eviction, or leave an unhandled rejection. `#announce` wraps the emit in `MaybePromise.catch`, which covers both the synchronous throw and the rejected promise.
- **Eviction is reported, and `allowEviction` gates only the taking rung.** `ResolvedStream.evicted` carries the ids, so a caller can see what serving it cost, and `allow_eviction` defaults to true because with reuse, the budget and narrowing ahead of it, taking a stream only happens where the alternative is failing the call. `allowEviction: false` breaks out before `freeAnUnreferencedVideoStream` and leaves the degraded rung reachable, because handing out an existing stream takes nothing from anyone. The default lives in `resolveVideoStreamLocked` and nowhere else: `parseStartStreamArgs` leaves an unstated `allow_eviction` undefined rather than filling it in, so the policy has one home.
- **`MediaDisposition` has four values because a nonzero port is not permission to send.** An `m=` section with port 0 is the peer declining that media kind (`refused`); no section at all is the peer having no place to carry it (`absent`); a live section whose direction is `a=sendonly` or `a=inactive` states that nothing sent into it reaches the peer (`notReceiving`); a live section the peer will receive on states that this kind reaches the peer through it (`receiving`), and it is the only state a track may be put into. Three of the four forbid the track, and `mediaRefusal()` takes the whole offer rather than one disposition so the fourth question — whether there is an offer at all — is answered with them: an answer carries exactly the m-lines of the offer it answers, in the same order (RFC 3264 §6), so an absent section is a refusal, while a `SolicitOffer` with no SDP refuses nothing because the camera writes the m-lines itself. Reading "no statement" as "no objection" is right on one of those paths and wrong on the other, which is why neither call site decides it. The direction answers two independent questions — may we send camera media here, and does the peer ask to send us audio — and `a=sendonly` answers no to the first and yes to the second, so `wantsTalkback` is read from the direction before the receiving test and never from the state. `mediaRefusal()` is the single read path for "may a track of this kind go in the answer", so no consumer can test one state and miss the other; `receivableCodecs()` is the single read path for the codec list and answers nothing for every state but `receiving`. Both refusals are answered where the track is decided, ahead of any narrowing: narrowing a codec set to empty is not how a caller learns its peer declined the media. The codec list has two meanings and only `receiving` carries it — a section carrying only statically-mapped payload types states nothing about what the peer decodes (`sdp-transform` builds `media.rtp` from `a=rtpmap` lines only), and narrowing by that empty statement is what refused a caller for a codec mismatch nobody stated. A section stating no direction is `sendrecv` (RFC 4566 §6) and a session-level direction applies to every section that does not restate it (RFC 4566 §5.13). Nothing in the Matter spec requires any of this: `sendonly`, `recvonly` and `sendrecv` do not occur in the appclusters chapters at all, and the reference camera app never reads the offer's direction — read in the local SDK checkout at `connectedhomeip/examples/camera-app/linux/src/webrtc-libdatachannel.cpp:440,451`, which hardcodes video `SendOnly` and audio `SendRecv` in its answer, and `.../clusters/webrtc-provider/webrtc-provider-manager.cpp`, which parses the offer only for `m=`, `a=mid:` and payload types. Re-read both before relying on that reasoning, since they are outside this repository. The reason for the four states is therefore this server's use of the camera's encoders and reference counts, not protocol compliance.
- **A track request has three states and one answer site.** `trackRequest(args.video)` reads the wire argument as `declined` (`false`), `deferred` (key absent) or `demanded` (key present, `{}` included). The resolvers never throw an absence: they return a `TrackOutcome`, and `CameraStreamManager.resolveTrack` is the only place that turns "no stream" into either a null track or the typed failure. Do not let a resolver decide that itself — video and audio answering the question in their own places is what produced a session with `video: null` and no error for a caller that had stated video bounds. What still differs is which outcomes reach `resolveTrack` at all: the audio resolver reports every dead end as `unavailable`, the video one reports only the offer's refusal and throws for the rest, because a camera refusing video is a failed session rather than an audio-only one.
- **Ownership is not permission to use, and eviction does not ask who allocated a stream.** `allocatedByUs` records one fact — this process run allocated the stream — and answers one question: what may this server deallocate on its own initiative. Reuse, adoption and `camera_release_stream` never consult it, because `VideoStreamDeallocate` (§11.2.8.7.2) and `AudioStreamDeallocate` (§11.2.8.3.2) refuse only an unknown id, `ReferenceCount > 0` and StreamUsage Internal, and `SnapshotStreamDeallocate` (§11.2.8.10.2) only the first two: none of them checks the allocator or the fabric. Do not reintroduce an ownership gate on any of those paths — a controller that refuses to take over an unused stream lets one client pin every encoder on the camera with streams nobody is watching, and has no remedy. Nothing about ownership is persisted; after a restart the device's own report is the record. `chooseEvictionVictim` takes this server's own streams before any foreign one and orders each side by the camera's `StreamUsagePriorities` (index 0 is the HIGHEST priority, §11.2.7.19). Ownership is the **primary** key and must stay there: `StreamUsagePriorities` is the camera's guidance for arbitrating between the streams it serves and states nothing about which controller should pay for a request, so ranking first destroys another controller's idle `LiveView` reservation while an idle `Recording` stream this server allocated sits untouched. That makes one rule for the whole make-room ladder — ours before anyone else's — which is also why `freeOwnSnapshotStream` runs first and offers only our own. Do not write down which usage the ranking makes safe: the order is the camera's and `SetStreamPriorities` (§11.2.8.12) reorders it, and this repo's own test fixture ranks LiveView above Recording, which is the reverse of the spec's example. A usage the list does not carry sorts last, because the camera states nothing about it and destroying what cannot be reasoned about is the one outcome with no way back.
- **What a finished `EndSession` means is decided in one place.** `deviceForgotSession` and `invokeEndSession` (`controller/webRtcSessionTracking.ts`) hold it: the server's local records of a session go when the device accepted the end and when it answered `NotFound` — the device answers that for any id it cannot resolve to one of its sessions (`WebRTCTransportProviderCluster.cpp`, `HandleEndSession` ahead of the delegate call) — and stay for any other failure, so a later stop, disconnect or shutdown still reaches the session. Every route that holds a record goes through it: `MatterCameraDeviceIo` drops the local requestor's tracking, `CameraStreamManager.#endSession` its registry entry, and the raw `device_command` path drops both, because it is not behind the camera io. Do not re-derive the status test at a call site. The one `EndSession` that does not go through it is `endSessionWithinBudget` in `webRtcSessionStreams.ts`, which tears down a session no record names yet and so has nothing to drop for any outcome. Routing the raw `EndSession` through `CameraStreamManager.stopStream` is not an option either — `stopStream` fixes the reason to `UserHangUp` and answers a boolean, so a client's own command would lose its reason and the device's response.
- **The camera's `CurrentSessions` is the record of which sessions exist; the registry is not.** `CameraSessionRegistry` lives for the process run, so after an ungraceful restart the camera still holds every session it established and only `EndSession` decrements the streams' `ReferenceCount`. `camera_stop_stream` therefore sends `EndSession` for an id it does not track instead of answering `ended: false`, and `camera_get_capabilities` reports `sessions` from the device so a client has an id to send. Do not put an ownership gate in front of that, and do not check the peer locally: `EndSession` (§11.5.6.7.3) fails `NOT_FOUND` unless the accessing fabric and `PeerNodeID` both match the stored entry, so the camera already ends a session of this server's or none, whatever id a client passes. `CurrentSessions` is fabric-sensitive (§11.5.5.1), which is what keeps another fabric's sessions out of the report without this server filtering; within the fabric `establishedByThisServer` compares the entry's `PeerNodeID` against `ControllerCommandHandler.localNodeId`, and an entry that is not this server's is still reported, because it is the only explanation a client gets for a `referenceCount` it cannot free. The registry keeps its two jobs — one `EndSession` per session however many paths reach it, and ending exactly the sessions a closing connection owned — and neither is reachable for a session from an earlier run, which is why the untracked path is a plain invoke rather than a registry entry synthesised from device data. The de-duplication therefore covers the paths that hold a record, not every `EndSession`: a stop that arrives after `invokeEndSession` dropped the entry and before the first release settles takes the untracked path and sends a second one, which the camera answers `NOT_FOUND` and this server reports as `ended: false`.
- **Restoring an evicted stream is not an undo, and no comment may say it is.** The camera issues a new `VideoStreamID`, so the controller that allocated the victim holds an id the camera has forgotten. What the restore puts back is the camera's capacity to serve a stream of that range and usage.
- **Every snapshot stream outlives its call, and the response always names it.** Adoption reads `AllocatedSnapshotStreams` fresh on every call and takes any stream that meets the caller's bounds and whose `minResolution` covers, per dimension, the capability that would be allocated — the ceiling states what the frame may be, not what it will be (§11.2.8.13.3), and pixel counts hide aspect-ratio loss. Device state lags, so an adopted id may be gone; the fallback is the device's own `NOT_FOUND` (§11.2.8.13.3), not a prediction from the leases. Nothing is deallocated by the snapshot call itself, not even a capability that holds one of `MaxConcurrentEncoders` (§11.2.6.13.9) — the video ladder's make-room rung is what takes such a stream back, under its own lock: the invoke carries no abort and the wait for it has to be bounded to keep the endpoint lock (`withCleanupBudget`), so a give-back could be started but never awaited to an outcome the response can state — an expired budget leaves the response naming a stream the abandoned deallocate may still remove, after the lock is gone and possibly under an id the camera has reissued. The lease generation guards this server's own record of such a landing; nothing can guard the device's copy. Reporting the id and deallocating anyway was the shape before this, and it is what makes the id the response hands out false after a budget expiry, so the give-back goes rather than the id. `stream_id` is therefore unconditional on a success: the stream is on the camera and its id is the one `camera_release_stream` takes. The cost is paid for in the encoder accounting: `encodersExhausted` counts an allocated snapshot stream whose `HardwareEncoder` is set (§11.2.6.13.9) whatever its reference count, so the next call narrows to a capability the camera can still serve instead of walking a ladder that has no rung left. What is left standing is that such a stream pins an encoder until something frees it: `camera_release_stream`, or the video ladder's make-room rung, which takes one of this server's own when it needs the capacity — but never the snapshot call itself, and error 103 still names the stream in `allocated` so a client can release it. Do not reintroduce a give-back here: the failure path's `returnOnFailure` deallocate is safe only because that answer names no id.
- **The snapshot encoder preference orders the ladder; it never shortens it.** `selectSnapshotCapabilities` puts the encoder-free capabilities first when `encodersExhausted` says every encoder is taken, and keeps the encoder-using ones behind them. Removing them ended the ladder at the last encoder-free rung: every rung can still be refused with `DynamicConstraintError`, and `encodersExhausted` reads a subscription-backed view that lags, so the device is the arbiter of whether an encoder is really free. Only the caller's own bounds and codec narrow the list, and a narrowing step that empties it reports `unsatisfiable`. `bestWithinCallerBounds` is computed before the ordering and is the best capability the caller's bounds allowed, which is what keeps `downgraded` from firing when the ladder reaches that capability through an encoder rung. The fallback's cost is that such a rung leaves an encoder-holding snapshot stream behind, which only `camera_release_stream` frees; error 103 names it.
- **A lease the camera never confirms lives for the process run, and `owned_by_server` can be wrong because of it.** There is no expiry: `retainUntil` was removed with the ownership-gated release it served. On a camera that never reports `Allocated*Streams` the per-endpoint lease list grows one entry per allocation, and on one that starts reporting late a reissued stream id can be matched to an earlier allocation, so the flag claims a stream this server did not allocate. That is now a reporting inaccuracy only — nothing gates on ownership any more — and it is the price of ownership meaning "this process run allocated it" and nothing else. A kept snapshot stream on such a camera is also unreachable through `camera_get_capabilities`, which reports what the camera reports; `camera_release_stream` still reaches it, because the snapshot response names its id and that command invokes the deallocate without consulting device state. §11.2.8.8 bounds that to one stream per snapshot capability, because an allocate for a matching request returns the id already issued.
- **One boundary turns a WebSocket payload into a WebRTC Provider argument.** `webRtcProviderArguments.ts` holds it, and both routes that carry client-stated provider arguments go through it from the WebSocket handler: `cameraCommands.ts` for the `ice_servers` and `ice_transport_policy` `camera_start_stream` takes, and `WebSocketControllerHandler.#handleSendWebRtcProviderCommand` for the whole `send_webrtc_provider_command` payload. `ControllerCommandHandler` has one provider entry, `invokeWebRtcProviderCommand`, and it takes matter.js-shaped fields only — no wire shape reaches that class, which is what keeps the conversion from growing a second copy there. The reason the boundary exists is `ice_servers`: the wire keeps the W3C `RTCIceServer` spelling — `urls`, one URL or a list — and `ICEServerStruct` (§ 11.4.5.3) spells the field `URLs` and always lists it, which matter.js camelizes to `urLs`, so a generic name conversion leaves the mandatory field unset and the failure is matter.js's TLV encoder rather than error 8. `WebRtcCallbackBridge` maps back for the `offer` event, so both directions of the wire use one shape. That mismatch is W3C-versus-Matter naming, which no model states, so it cannot live in the generic converter `device_command` uses — which is why `device_command` keeps taking the cluster's own spelling and is documented as doing so. Do not widen the parsed type to a record again, and do not add a second accepted spelling: a shape that works on one route and not the other is the seam this boundary closed. The `urls` key is also what the log redaction keys an ICE server on, so renaming it on the wire un-masks a TURN credential.
- **A wire key names a field when they differ only in case and underscores, and `camelize` cannot decide that.** `canonicalKey` in `webRtcProviderArguments.ts` lowercases and drops every non-alphanumeric character on both sides, which keeps it wider than `camelize` in every case: `camelize` splits on the same separators and never adds or removes a letter or digit, so a key it resolved still resolves. `camelize` reads `webrtc_session_id` as one word and answers `webrtcSessionId` where the field is `webRtcSessionId`, and leaves the W3C `sdpMLineIndex` alone where `ICECandidateStruct`'s field is `sdpmLineIndex` — both are spellings this API itself hands a client, one on `camera_start_stream`'s response and one on the `webrtc_callback` `ice_candidates` event, so matching by `camelize` refused a client's echo of the server's own words. The duplicate-key refusal is keyed on the same form, so two spellings of one field in one payload are still refused, and `contractFor` throws at load if two fields of one command or struct share a canonical key, which would make one of them unreachable. The one exception is an `ice_servers` entry: its keys are the documented ones exactly, because that entry is not the cluster's struct under another spelling — `urls` may be one string where `URLs` is always a list — so its shape is this API's own and has one spelling.
- **A caller states the session's streams in one form, and the server never picks one for it.** `selectWebRtcStreamFields` refuses a `ProvideOffer` / `SolicitOffer` request carrying both the revision-2 lists and the singular ids they deprecate, because the provider fails such a command with INVALID_COMMAND and its test spans both media kinds rather than each on its own (§11.5.6.1 and §11.5.6.3, Effect on Receipt). The refusal is unconditional, which is stricter than the device for a `ProvideOffer` re-offer — that test sits under `WebRTCSessionID == NULL` (§11.5.6.3) — and costs nothing a re-offer could have used, because the provider's whole stream-selection step sits under that same condition. The lists' own conformance does not forbid them there: `[(Rev >= v2) & (WebRTCSessionID == NULL)].d+, O` ends in a clause that leaves them optional, so a re-offer stating them is logged and forwarded rather than refused (`reportFieldsPastTheirGate`, next note). Do not go back to deleting one form: `{ videoStreams: [5], audioStreamId: null }` states a video stream and auto-selected audio, and dropping the id opens a video-only session and reports success for it. The one conversion left is a list going to a provider this server does not know to be at revision 2 — one stating revision 1, and one whose revision has not been read yet, which is the same position, because a list such a provider does not understand is dropped on receipt and the session comes up with streams nobody chose. The refusal says which of the two it is, since only one of them is the camera's doing. Such a provider carries one id per kind: a single-entry list says exactly what the singular id says, and that conversion is what keeps `camera_start_stream` — which always builds single-entry lists — working against such a camera. A longer list cannot be said at all and is refused rather than truncated. `resolveWebRtcSessionStreams` stays tolerant and keeps its filtering, because its inputs are device data — a `WebRTCSessionStruct` the camera reports and the provider's own stream-id echo — where an entry this server cannot parse is one it reports nothing about, not one it can refuse. `originatingEndpointId` is the one field still dropped rather than refused, and it is not the same case: it is server-owned, its only correct value is the requestor endpoint the client cannot know, and the injection changes nothing the caller can observe about the session it gets.
- **The provider boundary relays four commands, and only two of them establish a session.** Which ones is stated by `establishesWebRtcSession` beside the command list, and read by `WebSocketControllerHandler`, which then calls one of two entries on `ControllerCommandHandler`: `invokeWebRtcProviderCommand` for the establishing pair, whose signature takes only those two names, or `invokeWebRtcSignallingCommand` for `ProvideAnswer` and `ProvideIceCandidates`, a plain invoke returning nothing whose matter.js command name comes from `SIGNALLING_INVOKE_NAMES`, a `Record` over the name type so a name added to the list without a mapping does not compile. The split is made at the WebSocket route and not inside `ControllerCommandHandler` because a branch in that class is not reachable from any test without a live controller — round 8's mutation M10 was green for exactly that shape. Both signalling commands signal into a session the camera already holds; the model gives neither a response type, so the route answers `null`, and the camera answers for a session id it cannot resolve to one of its own. Do not route either through the establish path: they carry no `originatingEndpointId`, and that path reads a session id out of a response they do not have. `EndSession` is deliberately not on the list: `camera_stop_stream` owns it, because one session gets one `EndSession` and the two local records go with that invoke (see the `EndSession` note above).
- **The managed camera API completes a session, and the two signalling commands are how.** `camera_provide_answer` and `camera_provide_ice_candidates` exist so a `camera_start_stream` caller never has to name a cluster field or fall back to `device_command` mid-session; before the round that added them, `mode: "solicit_offer"` could not be finished through the managed API at all, since the camera's offer arrives on `webrtc_callback` and the answer has to go back as `ProvideAnswer`, which nothing but `device_command` relayed. They convert nothing of their own: `parseSignallingArgs` checks the argument object and the key set the way the other camera commands do, drops `node_id` / `endpoint_id`, and hands the rest to `toProviderCommandFields` as that command's payload, which works because `canonicalKey` resolves `webrtc_session_id` and `ice_candidates` to the fields they name. A second conversion here is the seam round 8 closed; the only thing the camera route adds is the `subjectName` that makes a refusal name `camera_provide_answer` rather than a cluster command the client never wrote. Neither command checks the session against this server's records, for `camera_stop_stream`'s reason: the camera holds the session, its `PeerNodeID` and fabric test decides, and this server's records name only its current run. Ownership decides which connection *receives* a session's signalling, never which connection may send it.
- **A client's own `EndSession` goes through `endedByClient`, the peer's `End` through `forgetSession`, and only the first announces.** The generic `device_command` route is the only way to send `EndSession` by hand, and it is that route's own end of the session, so it is announced by `camera_stop_stream`'s two rules: a session an entry names to that entry's owner, naming `requestedBy` so the asker is not told what its own response says; a session no entry names with no owner, which every route reads as "tell everyone". The third argument is the camera's answer: `invokeEndSession` drops records on its `NotFound` as well, and announcing an id **no** entry named then would report a session neither side ever had — for an id an entry did name, `NotFound` is still announced, because that session is gone either way. `forgetSession` announces nothing: round 18 routes the peer's `End` to the owner as a `webrtc_callback` event.
- **A session leaving the registry on a release path is announced, and who is told is decided from two names.** `CameraSessionRegistry.forgetEstablished` announces every drop through the callback the manager gives it, carrying the session's `ownerId` and the `requestedBy` of the command that caused it — a `camera_stop_stream`, or an `EndSession` on the generic `device_command` route — absent when the server ended the session itself. The route tells the owner and nobody else, and never the connection named by `requestedBy` — it has the answer to its own command. An `EndSession` the camera answers `NotFound` for still drops the entry (`invokeEndSession` decides that for every route) and is still announced: our record said the session was live, the camera says it holds none, and it is gone either way. A second emit site exists that no entry passes through — `#announceUntrackedEnd`, for a session this server ended and holds no record of — and it names no owner, which the route reads as every camera-aware connection but the asker. Do not add a reason field back: with the peer's `End` on `webrtc_callback`, a client's own command answered by its own response, a closing connection being the only party its own sessions concern, and every socket closed before the shutdown pass ends the sessions, the endings a client can be told about are another connection's stop and another connection's `EndSession`. - **A registration in flight is what catches a session that ends before it is tracked.** `establishWebRtcProviderSession` upserts the session with the local requestor *before* it returns, so an `End` can be routed, and the registry reached, while `#sessions.track` has not installed the entry yet. The fix is an ordering, not a guess: the provider helper calls `sessionEstablishing` with the answered id **before** the upsert — the requestor answers `NotFound` for a session it has not stored, so no `End` for that id can have arrived yet — and `CameraSessionRegistry.establishing` puts it on the registration. `forget` then marks only the registration whose own id the ended one is, and `track` answers `"already_ended"` for it, the third state of a refusal that used to be a boolean; the token is cause-neutral because the peer, another connection's `camera_stop_stream` and another connection's `EndSession` all reach the same mark and none of them is knowable from the id. **Every path on which this server learns a session has ended must go through `forget`**, including `#endUntrackedSession`, which has no entry to drop and calls it anyway — that is the invariant, and the one caller that skipped it left the whole hole open on a documented command. Never mark on node and endpoint alone: a camera reissues an id it has freed, and a registration waits through the endpoint lock as well as its own round trip, so a match that loose refuses live sessions other clients just established. For the same reason an id an entry *did* name is not marked: the camera cannot have issued it again while it still held it.
- **`webrtc_callback` is routed by the session's owner, and an unowned session is broadcast.** `CameraSessionRegistry.signallingOwners` answers it and is the only reader of a session's `connectionId` for this purpose: a tracked session names its one connection, and nothing else names any. `undefined` means this server holds no record at all — a raw-route session, one whose entry is already dropped, or one inside the window between `upsertSession` and `track` — and the WebSocket route sends those to every opted-in connection: withholding them would strand a session no client can complete. Do not turn that into a refusal, and do not give the raw route a registry entry to fix it — an entry makes a closing connection send `EndSession`, which is a behaviour change to a documented route. Do not make a registration still in flight an owner either: it names the establishing connection for every id the registry does not know, so it withholds a raw-route client's own signalling for as long as any `camera_start_stream` runs on that camera, and what it would buy is only that one window — `WebRtcTransportRequestorServer` answers `NotFound` for every signalling command naming a session it has not stored, `Offer` included, so nothing arrives before the registration. The id a peer ends is dropped from the registry *after* the emit, in `MatterController`, because the entry is what names the owner and every connection resolves that from its own observer of the same event; dropping it inside the emit sent an `end` to every connection registered behind that observer, which is every connection opened after the first camera command. The node id is branded through `NodeId()` at the route because the method takes one; the registry's key is a template string today, so a plain number matches it by coincidence, and a key that ever compared the id itself would then match nothing.
- **Every other provider field is converted from its own model definition, and a struct must be named.** `converterFor` reads each permitted command's field's type and constraint out of `@matter/model` and builds the check from them, and `contractFor` reads its conformance and nullability beside it, so a field added by a spec revision is bounded without being written out here. `STRUCT_CONVERTERS` is keyed by the struct the model names, not by the field carrying it, so a later field that happens to share a name cannot inherit another struct's conversion. A struct whose wire object is the cluster's own under this API's spelling — `ICECandidateStruct` — converts from the model like any other field, through `structConverter`; one whose wire shape is this API's own — `ICEServerStruct`, where `urls` may be a single string — has a written converter. Two things throw instead of returning a converter: a struct-typed field `STRUCT_CONVERTERS` does not name, in `converterFor` itself so a struct reached through a list raises the same error, and a scalar type `fieldRange` has no width for. Both run at module load over every field of both commands, and `WebSocketControllerHandler` imports this file, so a `@matter/model` whose provider commands this file cannot describe stops the server at startup rather than failing the first offer — as `cameraFieldRanges.ts` already does for the camera commands. That is the deliberate trade: such a model is a build mismatch, and a loud start beats a command that fails on a device the operator will blame instead. It is also what keeps the next struct field from being converted on one route only. `originatingEndpointId` is dropped at the boundary, not checked: `establishWebRtcProviderSession` injects the requestor's own endpoint over it.
- **`enum8` is bounded by its width, not by its defined values.** `streamUsage` on the raw route therefore takes any 0-255, `Internal` included. That is the raw route's business — it exists for a client doing its own allocation — while `camera_start_stream` takes a usage by name and refuses `Internal`, because there the server is the one allocating. `TYPE_MAX` is shared with `CAMERA_FIELD_RANGES`, so an enum field added there is bounded by its width too rather than failing the import.
- **The connection tag in the log lines is not an identity.** `nextConnectionLogTag` is four hex digits and wraps after 0xffff, because a human reads it as a column; `nextConnectionOwnerId` counts in `bigint` and therefore never repeats, and is what a camera session is owned by, so `releaseConnection` cannot end a second client's sessions after a wrap. Nothing else may be keyed on the tag.
- **One rule decides what `args` is, at the dispatch, for every command.** `commandArguments` (`WebSocketControllerHandler.ts`) substitutes `{}` for a missing or null `args` and refuses anything that is not an object with error 8. The substitution is the Python Matter Server's own reading (`parse_arguments` treats `args=None` as `{}`, `matter_server/common/helpers/api.py:53`; the non-dict path was read and run in that project's own checkout, not in this repository), and it is what lets a command whose arguments are all optional answer a one-line frame; handlers had begun writing `args ?? {}` one at a time, and the ones that had not — `set_loglevel`, `get_vendor_names` — reported error 0 for it. The refusal is stricter than the reference, which dies on a non-dict `args` while decoding `CommandMessage`, with an `AttributeError` its per-message `except ValueError` does not catch, and closes the connection without answering. Do not add a per-command shape check for this; a command's own required arguments are still its own to check, and a missing `node_id` on a node-targeted generic command still reaches `NodeId()` and is reported as error 0. The shape is checked before the command is looked up — there is no runtime list of commands to look it up in, only the dispatch switch — so a frame that states an unknown command *and* a non-object `args` answers 8 rather than 9. A command that is not a string skips the check and falls to the switch's default, which answers 9.
- **A field's conformance is read from the model, including the condition it is gated on.** `contractFor` (`webRtcProviderArguments.ts`) records, per field, the fields its conformance compares to null — `nullComparedNames` walks the `Conformance.Ast`, so `VideoStreams`, `AudioStreams`, `StreamUsage` and `MetadataEnabled` come out of `ProvideOffer`'s own definition rather than a list here. `reportFieldsPastTheirGate` logs a warning when a request states such a field while its gate holds a value, and forwards the payload untouched. Three of the four end their conformance in a clause that leaves them optional whatever the session id, so refusing those would state a rule the cluster does not; `MetadataEnabled` (`METADATA & (WebRTCSessionID == NULL)`) has no such clause and does not apply on a re-offer, and is forwarded anyway because what a device does with a field it did not ask for is the device's answer to give. The provider's Effect on Receipt reads none of them on a re-offer, which is what the log says. `OriginatingEndpointID` carries the same gate and is *not* covered: the boundary drops it before the contract is built, since the server injects its own. Do not turn this into a refusal or a drop without a spec line that says the device refuses it.
- **Every camera command's argument shape and keys are checked where its target is parsed.** `parseCameraCommand` refuses `args` that is not an object before the key check runs — `Object.keys` reads a string's indices as argument keys — and hands the caller's fields back, so no command can read a field before that refusal. Every parser therefore takes `unknown` and reads every field from what the guard returned. `send_webrtc_provider_command` walks a client's argument keys too, so it asks the same `requireArgumentObject` first and reads its node and endpoint through the same `parseTargetIds` — the branded ids are built from checked values on both routes, rather than `NodeId()` turning a fractional `node_id` into an uncaught `RangeError`. `parseCameraCommand` is named the command being parsed and refuses a key outside that command's set, so the rule reaches every camera route through the one call each of them already makes rather than through a line per command. The set is the command's, not the target check's own: it reads `node_id` and `endpoint_id` and nothing else, so a key it does not know is that command's own argument. `CAMERA_ARG_KEYS` is the only place a command name is paired with a key set, so the keys checked and the command named in the refusal cannot drift apart. Each set is a `Record` over the command's own `ArgsOf<>` type, so an argument added to the wire model and not listed does not compile. Nested objects check their own keys where they are parsed — the `video` / `audio` hints, an `ice_servers` entry, and a resolution, whose `{ width, height, frame_rate }` would otherwise state a bound nothing reads.
- **Wire numbers are bounded per field, from `@matter/model`.** `cameraFieldRanges.ts` reads each field's constraint and falls back to its scalar type's TLV width; `cameraCommands.ts` checks against those. A "positive safe integer" predicate is not enough — a value past a field's width reaches matter.js's TLV encoder and returns its error instead of error 8, and for an id it is worse than that: `camera_stop_stream` answered `ended: false` for a `webrtc_session_id` no session can have, which a client reads as a session that already ended. The ids are read from the command fields they become — `EndSession.WebRtcSessionId` and the three `*StreamDeallocate` fields — not from their datatype, so a constraint a future spec revision puts on the field is picked up.
- **`node_id` is bounded in `parseTargetIds`, because nothing downstream bounds it.** `NodeId(v)` is `BigInt(v)` and validates nothing, so a negative id is branded and reaches the node lookup, which answers `NODE_NOT_EXISTS` — a target no node id could name, reported as one this server does not hold. A bigint is bounded by `UINT64_MAX` from matter.js rather than by a literal, since a node id is 64 bits (Core § 2.5.5). A number is required to be a *safe* integer, not just an integer: past that range a double no longer holds every integer, so the value cannot be trusted to be the one the client wrote (`9.007199254740993e15` arrives as ...992). `parseBigIntAwareJson` reads a plain integer literal past `Number.MAX_SAFE_INTEGER` as a bigint, so what reaches the check as a number is an exponent-form literal. `webrtc_session_id` and the three stream ids need none of this — `isInRange` already requires a plain safe-integer number inside the field's own uint16 range. Not bounded and known: `endpoint_id`'s `0xfffe` is a literal, a node id that is not an *operational* one (0, the group and CAT ranges) is still accepted, and `device_command` brands its own `node_id` without going through here at all.
- **An `a=fmtp` line whose payload type has no `a=rtpmap` names no codec, and is dropped.** Every video codec this server can select is dynamically mapped, so such a line can only belong to a statically-mapped payload type (RFC 3551) that is none of them. There is nothing to attribute the limit to, and attributing it to another payload type's codec would clamp a stream by a bound that codec never stated. Do not "recover" these lines.
- **A request reaches the debug log before anything has looked at it, so redaction is by shape, not by command.** `redactSensitiveCommandFields` (`@matter-server/ws-client`) walks `args` and masks an explicit list of field names, matched with case and underscores removed because the same field arrives as `setup_pin_code`, `setupPinCode` or `PINCode`. Masked anywhere: setup codes and passcodes, Wi-Fi passphrases, Thread datasets, and symmetric key material — every name on the list carries nothing else, in this API and in the Matter command set a `device_command` payload reaches, which was checked against `@matter/model` rather than read off the names. Masked only inside an object that also states `urls`: `username` / `credential`, because that is what makes it an `RTCIceServer` (webrtc-pc §4.6.2) and it keeps the Door Lock `credential` struct — no secret, and worth reading — in the log. The names are matched whole, which is what keeps KeypadInput's `keyCode` — the concatenation of two masked names, and a remote-control key, not a secret — in the log. Only requests are walked, so a name that is harmless in a response (Door Lock's `GetUserResponse.Credentials`) can still be on the list; nothing masks a response at all. `skipMessageContentInLogFor` is the only lever there and it drops the whole payload, which is why `camera_snapshot` (the frame) and `open_commissioning_window` (the setup passcode and the codes carrying it) are named in it. A `device_command` response can still carry a Thread dataset or a Wi-Fi passphrase, and nothing stops that today. A WebRTC session's secrets are masked in both directions: `redactIncomingMessage` masks `a=ice-ufrag`, `a=ice-pwd` and an ICE server's `username` / `credential` anywhere under a message, and is what the client logs incoming frames and events through, because a `webrtc_callback` offer carries the camera's own. The same entry point states a string past 1024 characters by its length, which is how the client keeps a `camera_snapshot` frame out of a browser console: a response names no command, so a rule keyed on the command name cannot exist there, and this one needs nothing kept in step with `skipMessageContentInLogFor`. It replaces no entry in that list either. The rule trims one long string at a time, so it does not shrink a `start_listening` or `get_network_topology` response, which is wide rather than long, and it never sees `setup_pin_code`, which is a number. It is the incoming path's rule alone — an outgoing argument is logged whatever its length, because it is the record of what the caller asked for — and it reaches a value wherever it sits, a bare array entry included, because the walk takes a value rule beside its member rule. Every field beside the bulk one is logged, so the snapshot's codec, resolution and stream id survive, and an `sdp` is answered by the member rule ahead of the length rule and so keeps its lines. Both are matched by shape — a URL member beside the pair, a string under `sdp` — which is what makes the rule safe in either direction, unlike the field-name list. Nothing else in an offer is masked — the DTLS fingerprint is the peer's published binding to its certificate, not a secret — and the field-name list is not applied to an incoming message, whose names are a response's and mean other things. Everything else reaches the log unchanged on purpose: a request the log cannot show is a request nobody can debug. A new argument that can carry a secret is masked here, not at its command.
- **A device fact the report carries is the only fact a refusal may name.** `camera_get_capabilities` reports the AVSM `FeatureMap` as `features` and the three privacy attributes as `privacy`, read where every other device fact is read: `stateOf` for the attributes, and `globalsOf(CameraAvStreamManagementClient).featureMap` for the feature map, which `stateOf` leaves out of its shape. The report exists so a client never reads a cluster attribute to use this API, and the refusals are keyed to it: a demanded video or audio track on a camera that does not advertise the feature fails 102 `reason: "capability"` with `feature` naming it, and `featureName()` takes the model's own feature key so a refusal cannot name a feature the report never lists. A track the caller *left to the server* resolves to absent through `resolveTrack` instead — the one place that decision is made, so no third state appears for "this camera has no video". The offer's refusal is still tested ahead of the feature, so a demanded video track whose offer also carries no video section answers without a `feature`: both facts are true, and the peer's own statement is the one the caller can act on. The video gate sits at that call site while the audio one sits inside `resolveAudioStreamLocked`, for the reason the note above gives for the offer refusals: the video resolver throws rather than reporting outcomes, so both of its "absent is acceptable" cases are answered where the track is decided. The snapshot gate is ahead of the capability ladder rather than a label on its empty-list refusal, because `SnapshotCapabilities` is only usually empty on a camera without the feature — one that lists capabilities anyway would otherwise walk the whole ladder into a `SnapshotStreamAllocate` its `AcceptedCommandList` does not carry. `lacksFeature` is the one read path for "this camera cannot do that", and it answers false for a feature map that has not arrived: matter.js defaults the client's map and fills it from the device's report, so it advertises nothing until then, while at least one of Audio, Video and Snapshot is mandatory (§11.2.5), which makes none of the three "not stated yet". Reading that as "no video" would strand a real camera in an audio-only session, which is the opposite mistake from the one the gate prevents, so an unstated map means the device gets the request and answers for itself — what every release before the map was read did. A feature map this server cannot read at all — a raw bitmap where the flag object is expected — degrades the same way rather than dangerously: every flag reads absent, so nothing is gated and nothing is reported. `statedFeatureNames` applies the same test to the report, which is why `features` is *absent* rather than empty for such a camera: a list a client has to apply that rule to itself is a report and a refusal using two definitions of one fact. Which features a present list names is read from the map alone and their spelling from `CameraAvStreamManagement.Feature`, so a flag the model stops naming is reported under its own flag name and sorted last instead of silently disappearing from the list; a title rebuilt from the flag name would break on the first feature whose title starts with an acronym. `hdrCapable` is read from the feature map for the same reason the gate is: `HDRModeEnabled`'s presence could not tell a camera without the feature from one whose attribute had not arrived.
- **Nothing is checked against the privacy switches ahead of an invoke.** `privacyFailure` runs only on a device rejection, and only for `INVALID_IN_STATE`, which is what the provider (§11.5.6.1.10, §11.5.6.3.12) and `CaptureSnapshot` (§11.2.8.13.3) answer for a privacy switch — and also what they answer for several things that are not privacy, a `turns:` ICE server on a camera whose `UTCTime` is null among them, so the reported switches are what tells the cases apart and a status no switch covers stays the device's own error. The allocates are deliberately not on that path: `VideoStreamAllocate` (§11.2.8.4.12), `AudioStreamAllocate` (§11.2.8.1.7) and the deallocates answer `INVALID_IN_STATE` for a stream usage that is not in `StreamUsagePriorities` and for a reference count above zero, and privacy is not in their Effect on Receipt at all, so mapping their status to a privacy switch would name a fact the device did not state. A pre-check was considered and rejected for `releaseStream`'s reason: the switches come from a subscription-backed view that lags in both directions, a refusal decided on a stale "on" leaves no path that reaches the device, and a stale "off" costs only this mapping, which the pre-check would not have fixed either. The state is re-read inside `privacyFailure` rather than taken from the state the call started with, because a report that arrived in the meantime is what makes the answer nameable. The usage gating is the spec's: soft livestream privacy covers `LiveView` and soft recording privacy covers `Recording` and `Analysis`, while a snapshot carries no usage and is covered by the hard switch and the livestream one. Both directions are tested, because widening a switch's reach is the mistake a test that only checks the covered usage cannot see. `modes` names every switch that forbids the call and the documents claim no order between them: the device answers one status for all of them, and the reference `CaptureSnapshot` tests the two in a single condition, so "the first entry is the one it answered on" would be a claim the device does not make. Error 106 rather than a 102 `reason` because every 102 reason can be answered by asking for something else and this one cannot.
- **Open, recorded here because the notes they came from are not committed:** codec choice takes `candidates[0]` from the device's or the caller's order and never the offer's m-line preference order, which now also decides whose `a=fmtp` limits apply; and capacity decisions read `referenceCount` from a subscription-backed cache the session registry could answer more accurately. `releaseStream` is the one place that does not decide on that cache: the deallocate always goes out and the camera's own `INVALID_IN_STATE` is what raises `camera_stream_in_use` — the reference implementation answers it for a reference count above 0 and for nothing else, and passes its delegate's status through, so the device error is kept as the cause — because a stale count is wrong in both directions — a stale zero used to surface the device's refusal as error 0, and a stale non-zero refused a release the camera would have accepted with no path left that reaches the device. The cached count only fills in the detail. Do not put the count back in front of the invoke.
- **The overlay flags are a caller bound, a server default, and a conformance rule at once.** `WatermarkEnabled` / `OSDEnabled` are conformance `WMARK` / `OSD` on both `VideoStreamAllocate` (§11.2.8.4) and `SnapshotStreamAllocate` (§11.2.8.8), which the reference server enforces as a biconditional — `HasFeature(Feature::kWatermark) == commandData.watermarkEnabled.HasValue()`, `INVALID_COMMAND` either way — so omitting the field on a camera that advertises the feature and sending it on one that does not are the same error, and `ladderReaction` maps it to `rethrow`. `overlayPolicy.ts` is the only place that rule lives: `resolveOverlays` turns what the caller stated plus `overlaySupport(state.features)` into the fields to send. There is no second derivation for a stream the camera already reported — `AllocatedVideoStream.overlays` keeps the camera's own optionality and is carried across unchanged, which is what makes the same value the honest report for a reused or degraded stream *and* a conformant request again for `#restoreFreedVideoStream`. An earlier shape derived the restore's fields from the feature map instead, and that both dropped a victim's overlays while the map was unstated (`INVALID_COMMAND` for the replacement on a camera that does have the feature, and a picture put back without its watermark) and reported `false` for a reused stream the camera called watermarked. `overlaysMatch` is the one place an absent flag reads as off, and the wire boundary (`toWireCapabilities`, `toWireStartStreamVideo`) is the only other `?? false`. Four things are decided in `overlayPolicy.ts` and must not be re-decided elsewhere. First, an unstated overlay goes out as `false`, because a `WMARK` camera has to be told something and §11.2.6.11 gives both `VideoStreamStruct` fields a fallback of 0 — that is the spec's own reading of a flag nobody stated, not a preference. Second, a stated `false` on a camera advertising neither feature is *met* by sending nothing, while a stated `true` there is 102 `capability` with `feature` naming it: without the feature there is no overlay, so `false` is honoured and `true` is unreachable by any narrowing. Third, an unstated feature map gates nothing, exactly as `lacksFeature` does: the caller's own statement reaches the device and a caller that stated nothing sends nothing, which is what every release before this did — so the biconditional holds for a camera that has answered and for nothing else, and the client-facing documents say so. Fourth, an absent flag on a *stream* reads as off only inside `overlaysMatch`, because everywhere else that absence is also what says the field must not go on an allocate. In the gate the split is the existing one, not a new concept — a *stated* flag is a caller bound and lives in `satisfiesVideoCallerBounds`, hard at every rung including the degraded one; an *unstated* flag resolves to `false` on the envelope, so `fitsComputedEnvelope` binds the reuse rung and the degraded rung may give it up and say `degraded: true`. Do not move the unstated case into the caller bounds (it would make the degraded rung unreachable for a caller that said nothing) and do not drop it from the envelope (two identical calls would then get visibly different pictures depending on what happens to be allocated). Two honest limits are documented rather than coded around: the reference's own dedup (`UpdateVideoStreamRangeParams`) intersects the range parameters only and never touches the overlay flags, so a camera returning an existing id for a matching allocate keeps that stream's overlays whatever the request asked for; and §11.2.8.8.6 lets a camera ignore both fields on a snapshot capability whose `RequiresHardwareEncoder` is false and apply the source video stream's setting instead, which is logged and stated in the client documents but never acted on — gating on a MAY would mean dropping a caller's request on a guess. The cost of not acting on it is bounded and is the right way round: such a camera reports flags that differ from the resolved ones, so `findAdoptableSnapshotStream` stops adopting and every call re-allocates, which §11.2.8.8's own dedup answers with the same id. One extra invoke per snapshot beats handing out a picture carrying an overlay the caller stated against. `VideoStreamModify` / `SnapshotStreamModify` are deliberately not exposed: §11.2.8.6 checks the id, the state and `Internal` and nothing else, and §11.2.8.11's list differs again (no `Internal`, plus a `DYNAMIC_CONSTRAINT_ERROR` for a capability needing no hardware encoder); neither checks the reference count or who allocated the stream, so a modify writes to a stream other controllers may be watching, which is the inverse of the one-owner invariant — and nothing needs it, because a caller wanting different overlays is served by a stream of its own.
