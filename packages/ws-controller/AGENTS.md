# ws-controller — non-obvious invariants

- **Typed state vs. attribute cache.** Wire serialisation (`AttributeDataCache.ts`) reads the attribute cache and flattens struct fields to numeric-tag-keyed objects for the Python-compatible protocol. Decision logic — anything that branches on a device's current state, such as `packages/ws-controller/src/camera/` — reads `endpoint.stateOf(XxxClient)` instead. The cache's flattening is lossy: a mis-keyed lookup returns `undefined` rather than a type error, and a default can then silently stand in for real device data (issue #1054). `stateOf` gives typed fields, so the same mistake is a compile error instead of a silent wrong answer. Do not add cache reads to new decision code; if a subsystem needs both (serving state over the wire and deciding on it), read `stateOf` once and serialise from that, rather than reading the cache a second time for the same fact.
- **SDP `a=fmtp` limits are per payload type, never per offer.** `sdpConstraints.ts` keys them by codec, and `videoCodecLimits(sdp, codec)` reads them out tagged with that codec. Do not reintroduce a flat `maxPixels` / `maxBitRate` on the offer: browsers offer H.264 and H.265 with different level caps, and one folded ceiling clamps the selected codec to the other codec's limit. `max-fs`, `max-mbps`, `max-fr` and `max-br` are parsed. Note what is *not*: `profile-level-id` (H.264), `level-id` and `max-fps` (H.265), which is where a peer usually states its real ceiling, so a codec offering only a level is unconstrained here. Reading a level means mapping it onto the per-level luma picture size and sample rate tables, which is a table with its own correctness surface and no hardware here to check it against.
- **The offer's limits are a decode ceiling, not a preference.** They live in `VideoCallerBounds`, so `satisfiesVideoCallerBounds` applies them and every rung that hands a stream out — reuse, make-room, degraded — is bound by them. A rung may give up the envelope the server computed; video the peer cannot decode is not a degraded picture, it is no picture. `offerFrameRateCeiling` is shared by the envelope and the gate so the rate the server allocates at and the rate it accepts a candidate at cannot drift apart.
- **`MediaDisposition` has three values because a refusal is not an absence, and its codec list has two meanings.** An `m=` section with port 0 is the peer declining that media kind; no section at all leaves the decision to the server. The parser used to read a rejected section as if the peer had offered it — its codecs narrowed the selection, its `a=fmtp` limits clamped the envelope, a rejected audio section could set `wantsTalkback`, and a stream was allocated and attached to the answer for it. Dropping the section instead is not the fix either: an offered section carrying only statically-mapped payload types states nothing about what the peer decodes, and narrowing by that empty statement is what refused a caller for a codec mismatch nobody stated. So `offered` carries its codec list only when the peer stated one, `offeredCodecs()` is the single read path for both kinds, and refusal is answered where the track is decided, ahead of any narrowing.
- **A track request has three states and one answer site.** `trackRequest(args.video)` reads the wire argument as `declined` (`false`), `deferred` (key absent) or `demanded` (key present, `{}` included). The resolvers never throw an absence: they return a `TrackOutcome`, and `CameraStreamManager.resolveTrack` is the only place that turns "no stream" into either a null track or the typed failure. Do not let a resolver decide that itself — video and audio answering the question in their own places is what produced a session with `video: null` and no error for a caller that had stated video bounds. What still differs is which outcomes reach `resolveTrack` at all: the audio resolver reports every dead end as `unavailable`, the video one reports only the offer's refusal and throws for the rest, because a camera refusing video is a failed session rather than an audio-only one.
- **Ownership is not permission to use, and eviction does not ask who allocated a stream.** `allocatedByUs` records one fact — this process run allocated the stream — and answers one question: what may this server deallocate on its own initiative. Reuse, adoption and `camera_release_stream` never consult it, because `VideoStreamDeallocate` (§11.2.8.7.2) and `AudioStreamDeallocate` (§11.2.8.3.2) refuse only an unknown id, `ReferenceCount > 0` and StreamUsage Internal, and `SnapshotStreamDeallocate` (§11.2.8.10.2) only the first two: none of them checks the allocator or the fabric. Do not reintroduce an ownership gate on any of those paths — a controller that refuses to take over an unused stream lets one client pin every encoder on the camera with streams nobody is watching, and has no remedy. Nothing about ownership is persisted; after a restart the device's own report is the record. `chooseEvictionVictim` picks the candidate furthest down the camera's `StreamUsagePriorities` (index 0 is the HIGHEST priority, §11.2.7.19). Do not write down which usage that makes safe: the order is the camera's and `SetStreamPriorities` (§11.2.8.12) reorders it, and this repo's own test fixture ranks LiveView above Recording, which is the reverse of the spec's example. A usage the list does not carry sorts last, because the camera states nothing about it and destroying what cannot be reasoned about is the one outcome with no way back.
- **What a finished `EndSession` means is decided in one place.** `deviceForgotSession` and `invokeEndSession` (`controller/webRtcSessionTracking.ts`) hold it: the server's local records of a session go when the device accepted the end and when it answered `NotFound` — the device answers that for any id it cannot resolve to one of its sessions (`WebRTCTransportProviderCluster.cpp`, `HandleEndSession` ahead of the delegate call) — and stay for any other failure, so a later stop, disconnect or shutdown still reaches the session. Every route that holds a record goes through it: `MatterCameraDeviceIo` drops the local requestor's tracking, `CameraStreamManager.#endSession` its registry entry, and the raw `device_command` path drops both, because it is not behind the camera io. Do not re-derive the status test at a call site. The one `EndSession` that does not go through it is `endSessionWithinBudget` in `webRtcSessionStreams.ts`, which tears down a session no record names yet and so has nothing to drop for any outcome. Routing the raw `EndSession` through `CameraStreamManager.stopStream` is not an option either — `stopStream` refuses an untracked id, fixes the reason to `UserHangUp` and answers a boolean, so a client's own command would lose its reason and the device's response.
- **Restoring an evicted stream is not an undo, and no comment may say it is.** The camera issues a new `VideoStreamID`, so the controller that allocated the victim holds an id the camera has forgotten. What the restore puts back is the camera's capacity to serve a stream of that range and usage.
- **A snapshot stream outlives its call unless it holds the hardware encoder.** Adoption reads `AllocatedSnapshotStreams` fresh on every call and takes any stream that meets the caller's bounds and whose `minResolution` covers, per dimension, the capability that would be allocated — the ceiling states what the frame may be, not what it will be (§11.2.8.13.3), and pixel counts hide aspect-ratio loss. Device state lags, so an adopted id may be gone; the fallback is the device's own `NOT_FOUND` (§11.2.8.13.3), not a prediction from the leases. Keeping a capability that needs the hardware encoder is what makes the next snapshot fail with `ResourceExhausted` on single-encoder hardware, which is why that one alone is given back.
- **A lease the camera never confirms lives for the process run, and `owned_by_server` can be wrong because of it.** There is no expiry: `retainUntil` was removed with the ownership-gated release it served. On a camera that never reports `Allocated*Streams` the per-endpoint lease list grows one entry per allocation, and on one that starts reporting late a reissued stream id can be matched to an earlier allocation, so the flag claims a stream this server did not allocate. That is now a reporting inaccuracy only — nothing gates on ownership any more — and it is the price of ownership meaning "this process run allocated it" and nothing else. A kept snapshot stream on such a camera is also unreachable through `camera_get_capabilities` and `camera_release_stream`, which read what the camera reports; §11.2.8.8 bounds that to one stream per snapshot capability, because an allocate for a matching request returns the id already issued.
- **Wire numbers are bounded per field, from `@matter/model`.** `cameraFieldRanges.ts` reads each field's constraint and falls back to its scalar type's TLV width; `cameraCommands.ts` checks against those. A "positive safe integer" predicate is not enough — a value past a field's width reaches matter.js's TLV encoder and returns its error instead of error 8.
- **The offer's direction is read for talkback only.** A video section with `a=inactive` or `a=sendonly` still counts as offered, so a stream is allocated for a peer that will not receive it, and an offer with no video section at all allocates video although `ProvideOffer`'s answer cannot add the m-line. Both are open; do not assume the disposition already covers them.
- **Open, recorded here because the notes they came from are not committed:** the two direction cases above; codec choice takes `candidates[0]` from the device's or the caller's order and never the offer's m-line preference order, which now also decides whose `a=fmtp` limits apply; an `a=fmtp` line whose payload type has no `a=rtpmap` is dropped; and capacity decisions read `referenceCount` from a subscription-backed cache the session registry could answer more accurately.
