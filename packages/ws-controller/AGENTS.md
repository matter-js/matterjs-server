# ws-controller — non-obvious invariants

Each entry: what must hold, what breaks if it does not, where it is enforced. Most apply to `src/camera/`.

## Device state

- **Decision logic reads `endpoint.stateOf(XxxClient)`, never the attribute cache.** The cache (`AttributeDataCache.ts`) flattens structs to numeric-tag-keyed objects for the wire; a mis-keyed lookup there returns `undefined`, and a default then silently stands in for real device data (issue #1054). `stateOf` makes the same mistake a compile error. A subsystem that both serves and decides on a fact reads `stateOf` once and serialises from that.

## SDP and codec limits (`sdpConstraints.ts`, `codecLevels.ts`)

- **`a=fmtp` limits are per payload type, never per offer.** `videoCodecLimits(sdp, codec)` returns them tagged with the codec. A flat `maxPixels` / `maxBitRate` on the offer clamps the selected codec to another codec's cap, because browsers offer H.264 and H.265 with different levels.
- **Parameter names and units are per codec, in `FMTP_PARAMETERS`.** H.264: `max-fs` / `max-mbps` in macroblocks, `max-fr` in frames per second (RFC 6184 §8.1, RFC 7741 §6.1). H.265: `max-lps` / `max-lsr` in luma samples, `max-fps` in frames per 100 seconds (RFC 7798 §7.1). `max-br` is units of 1000 bit/s in both. Reading H.264's `max-fs` on an H.265 record lets a token H.265 does not define lift the ceiling `level-id` stated. A codec with no entry falls back to H.264's names and units; removing that fallback would widen a bound an offer already states.
- **The level is a ceiling.** Treating a level-only offer as unconstrained breaks the rule this subsystem is built on. `codecLevels.ts` holds ITU-T H.264 Table A-1 (MaxFS, MaxMBPS, MaxBR) and ITU-T H.265 Table A.8 (MaxLumaPs) with Table A.9 (MaxLumaSr); each table cites its source because no Matter model states them. Rules that are easy to get wrong:
  - `profile-level-id` is three bytes and only the last is the level.
  - Level 1b has two spellings: `level_idc` 9, and `level_idc` 11 with `constraint_set3_flag` set on profile 66, 77 or 88 (H.264 §A.3.1, RFC 6184 §8.1). The second spelling is level 1.1 on every other profile.
  - An explicit capability parameter overrides the level's value rather than tightening against it; both payload formats define it as a capability at or above the level's.
  - H.264 MaxBR is taken at the Baseline / Main / Extended `cpbBrVclFactor`. High profiles scale it by 1.25, so the unscaled number is the tighter, safe bound.
  - No bit rate is derived from an H.265 level: H.265 states MaxBR per tier, and a guessed tier is not a bound.
  - The RFC default for an absent level (H.264 `42000A`, H.265 `level-id` 93) is not applied. H.264's is Baseline level 1, whose MaxMBPS bounds 1080p below one frame per second, so inferring it from a record stating only `max-fs` would refuse offers no peer meant to restrict.
- **A ceiling this server cannot read makes the codec unselectable, never unbounded.** `fmtpNumber` answers `absent`, `read` or `unreadable`. A value that is not whole digits (`max-fs=8160px`) puts the codec in `unreadableCeilingCodecs`; so does an unreadable level. Do not fall back to the level (the parameter overrides it) and do not read a digit prefix (a number the peer did not state). `decodableVideoCodecs` is the one read path that splits the set out; `preferredVideoCodec` refuses with 102 `reason: "level"` ("a decode ceiling this server cannot read") when nothing is left. The set is keyed by codec name, so one unreadable record blocks the codec for the whole session even where another payload type of it is readable. The codec stays in the section's codec list: a list narrowed to empty reads as "the peer stated no codec", which is unconstrained.
- **An `a=fmtp` line whose payload type has no `a=rtpmap` is dropped.** Every selectable video codec is dynamically mapped, so such a line belongs to a static payload type (RFC 3551). Attributing it to another codec clamps a stream by a bound that codec never stated.

## Video envelope, encoder budget, ladder (`streamPolicy.ts`, `CameraStreamManager.ts`)

- **The offer's limits are a decode ceiling, applied at every rung.** They live in `VideoCallerBounds`. The reuse and degraded rungs check them with `satisfiesVideoCallerBounds`; make-room uses that predicate only to keep such streams out of eviction. The allocate and retry rungs carry them through `computeVideoEnvelope` and `videoRetryWindow`, which only lowers ceilings. A rung may give up the computed envelope; video the peer cannot decode is no picture.
- **One frame-rate ceiling for envelope and gate.** `offerFrameRateCeiling` is shared by both so the allocate rate and the accept rate cannot drift. It may answer 0; rounding to 1 widens the peer's pixel rate at a resolution it cannot decode. `computeVideoEnvelope` spends the pixel-rate budget on frame size first, so the rate it allocates at is never 0.
- **The encoder budget only predicts; only the camera refuses.** `freeEncodedPixelRate` is `MaxEncodedPixelRate` (§11.2.7.2) minus what the camera's streams reserve. When a window costs more (`encodedPixelRate`), `fitToBudget` replaces it with the first one in the capacity order that fits (frame size first at the same rate, then frame rate), and that one is asked. When nothing fits, the smallest size at the wanted rate is asked. The search holds no predicted refusals, so `makeRoom` only follows a ResourceExhausted from the camera, and after room is made every window is fitted again with the freed room.
  - The cluster states no per-stream formula (§11.2.6.9.4 covers a snapshot capability only). The sum is copied from the reference server, `CameraAVStreamManagementCluster.cpp` `IsResourceAvailableForStreamAllocation`: `maxFrameRate × maxResolution` over every allocated video stream, plus `frameRate × maxResolution` over every snapshot stream with `EncodedPixels` set (§11.2.6.13.8). That is why `AllocatedSnapshotStream` carries `frameRate` and `encodedPixels`. Cite that function when the arithmetic is questioned.
  - The reference counts every allocated video stream against `MaxConcurrentEncoders`; `encodersExhausted` counts only referenced ones. Deliberate divergence, documented on `encodersExhausted`.
  - The budget never goes under a caller floor or the plan's floors, since it only picks among the search's own windows. A frame rate the budget lowered is restored as soon as the camera answers DynamicConstraintError to it, and the window at the higher rate is asked as it is: the camera may serve the higher rate. That refusal is not kept as a limit, so a later step (another bit rate or size) can have the budget lower the frame rate to the same rate again. Known limitation.
  - `freeEncodedPixelRate` answers `undefined` for a camera that states no budget, and every window fits. A spent budget (free ≤ 0) fits nothing, so the camera is asked the smallest size and decides.
  - Frame size is given up before frame rate for capacity, and a size step for capacity keeps the frame rate so the window charges less. Frame rate is the one dimension whose floor cameras do not publish.
  - `video.narrowed_by_encoder_budget` comes from `search.budgetNarrowing(accepted)`: the first window's frame rate or frame size ceiling the accepted window gave up, reported only when the budget moved at least one window. Allocate path only (a reused or degraded stream carries the camera's own range). It is not `degraded`.
  - Reuse is measured against the first window an allocate would ask within the budget if the candidate did not exist (`firstVideoWindow`, the candidate's own reservation freed): a stream at least that fast is reused. When no window fits, any stream within the plan is reused: an allocate could only succeed by freeing room or if the camera accepts a window the budget said would not fit, and reuse costs nothing.
- **The bit rate starts at 8 Mbit/s or lower.** `computeVideoEnvelope` starts at the lowest of the offer's ceiling, `MaxNetworkBandwidth` and 8 Mbit/s. `MaxNetworkBandwidth` is a link capacity, not an encoder limit, so it may lower the start but never raise it; only a caller-stated `max_bit_rate` or `min_bit_rate` sets a start above 8 Mbit/s. Live, a tested camera reports 128 Mbit/s and serves at most 2 Mbit/s.
- **Every window asks for one frame rate, with key frame interval 4000, except the certification window (last rung, below), which asks the frame rate range the CSA scripts use on purpose; do not narrow it to one rate.** Measured on a tested camera (reference camera app values): `VideoStreamAllocate` is accepted only when the whole window lies inside one of the camera's fixed profiles, whose frame rate floor (30), bit rate ceiling (2 Mbit/s) and key frame rule (exactly 4000) no attribute publishes. A range such as `1..30` or `15..30` is refused for that reason, so the frame rate window is `target..target` even when the caller states `min_frame_rate`: the target is the highest rate inside the caller's bounds, the offer and `maxFps`. Without a caller `max_frame_rate` the ceiling is `DEFAULT_MAX_FRAME_RATE` (30, raised to a higher `min_frame_rate`): a tested camera accepted 640x480 at 90 fps (the level 3.1 ceiling at that size) and sent black video. The certification window keeps the full allowed rate (`maxFps`, the caller's, the offer's) since it is a range the camera picks from. The cap limits only what is allocated: reuse (`fitsPlan`) checks against `VideoPlan.allowedFrameRate`, the uncapped rate. Otherwise a stream above 30 is neither reused nor evictable (it meets the caller's bounds) and comes back from the degraded rung after a full search, and a certification-window stream (30..maxFps) is never reused by the next identical request. `computeVideoEnvelope` returns a `VideoPlan`: that envelope and `frameRateFloor` (the caller's `min_frame_rate`, else 1), the lowest rate any window may ask. Reuse (`fitsPlan`) takes a stream whose maximum reaches the frame rate an allocate would end at and whose minimum is at or above `frameRateFloor`, so Auto never reuses a slower stream than it could allocate. Allocated streams carry their own `keyFrameInterval` (and snapshot streams their `quality`), which reuse reports and an eviction restore sends back. Reuse checks a stream's bit rate against the floor of the stream's own size.
- **Retries are one search over request windows (`videoWindowSearch.ts`), the only code that changes a request window.** `VideoWindowSearch` holds the steps (how often bit rate, frame rate and frame size were halved, and the rate frame rate counts down from), per-dimension limits, the window it wants and the window the budget made it ask, every window the camera refused with the camera's answer (`unservable`, `capacity`), and the best window refused for capacity. The ladder pulls `search.move` (`ask`, `makeRoom`, `giveUp`) and reports answers with `refused`, `roomMade`, `noRoom`. Each dimension in `RETRY_DIMENSIONS` states `unpublishedFloor` (frame rate) and `chargesEncoder` (frame rate, frame size), and the rules follow from them:
  - Unservable (207): step the first dimension in list order. The list order is the documented quality priority: bit rate goes first (unpublished profile ceilings; 2 Mbit/s on a tested camera), then frame rate, and frame size is kept longest (1080p@30 over 480p@60). An unservable frame size step restarts frame rate at the highest rate the offer decodes at the smaller size (`planFrameRate`). Each window's bit rate floor is the trade-off point for its own max resolution (`planBitRateFloor`); below every point it is the lowest floor any point states, and a floor above the start is dropped (plan floor: the caller's `min_bit_rate` or 1); and is the caller's `min_bit_rate` at every size when stated. A size step keeps the halvings taken.
  - Capacity (the camera's ResourceExhausted): step a `chargesEncoder` dimension with a published floor from the window asked (frame size, keeping the frame rate), then `makeRoom`, then on `noRoom` the `unpublishedFloor` one (frame rate). An unservable window steps from the window the search wanted, which the budget then fits again.
  - Floor found only on proof: a 207 right after a frame rate step from a window the camera refused for capacity (so servable under the reference app's profile-before-capacity order) caps frame rate there and returns to that window as capacity-refused. On the unservable path a lower frame rate is just another window, so a camera serving only 7 fps is reached.
  - A step never proposes a window the camera refused as unservable, or refused for capacity since room was last made (compared as the budget would fit it), and stepping passes over such windows: `roomMade` drops capacity refusals, because the freed room may carry them. Two moves can ask a refused window again: `roomMade` returns to the best capacity-refused window on purpose, but steps on if the budget now fits it to a window refused as unservable, and if no step is left it asks the first capacity-refused window as is, so every `roomMade` is followed by an ask; and the restore asks the higher rate after the camera refused a rate the budget lowered.
  - `outcome` is `capacity` once the camera refused any window for capacity (error 103), else `unservable` (102).
  - Last rung, `VideoPlan.certificationWindow`: the window the CSA certification scripts allocate (the codec's first trade-off point's bit rate as minimum and maximum, frame rate 30 up to the plan's maximum, the plan's size range), clamped into the plan and left out when the codec has no trade-off point, when the caller's or the offer's bit rate bounds exclude its bit rate, or when the frame rate allowed by `maxFps`, the caller and the offer is below 30 (or `frameRateFloor`); never by the server's floor, the 8 Mbit/s start or `MaxNetworkBandwidth`. Reuse (`fitsPlan`) accepts its bit rate range. While every refusal was unservable, `#settle` asks it once when the steps give up or on the last ask the limit leaves. A certified camera must accept it; it is the one window with a frame rate range. Refused for capacity, it is asked again after room is made. `sameVideoEnvelope` compares the minimums too, so it is not mistaken for a step window.
- **The ladder narrows before it evicts, and restarts after.** An eviction costs the victim's holder an id the camera forgets, and §11.2.1.1 asks commissioners to pre-allocate long-lived streams, so idle streams are usually reservations. `roomMade` returns the search to the best capacity-refused window: it was servable, so the freed room may carry it. Termination: frame rate and frame size have `BOUNDED_LIMITS` (2 each), bit rate halves to the floor of each size (`bitRateSteps`), refused windows are not repeated while the room stays the same (capacity refusals are dropped at `roomMade`, and every eviction is followed by an ask), and `makeRoom` removes every victim it tries from its candidate lists whether the deallocate succeeded or not (only a freed stream leaves the budget accounting), so the candidate lists strictly shrink. `MAX_VIDEO_ASKS` (32; re-exported as `MAX_ALLOCATE_ATTEMPTS`) bounds the device asks; the search counts them and answers `giveUp` past the limit, and the ladder makes room only while `search.asksLeft` is above 0. Bit rate has no fixed step count (`bitRateSteps`): it halves down to the trade-off point for the window's frame size, because profile bit rate ceilings are hidden (a tested camera refused 128M, 64M, 32M, 16M and 8M, then every frame rate and size step at 8M). All 207 is 1 + B + 2 + 2 × 3, where B is the halvings from the start to the lowest floor of any size (the count carries across size steps): 10 for 8 Mbit/s to a tested camera's 10000 bit/s, at most 22 from 8 Mbit/s to a floor of 1 (31 asks in all) when the camera states no trade-off point. A caller-stated start above 8 Mbit/s can make the cap cut the last size steps. `ladderReaction` maps `DynamicConstraintError` to `unservable`, `ResourceExhausted` to `capacity`, `ConstraintError` to fail-incompatible, everything else to rethrow.

## Eviction and ownership

- **One eviction order: own snapshot, own idle video, foreign snapshot, foreign video.** Own streams cost only this server. A foreign snapshot stream can be in use at `ReferenceCount` 0 (`CaptureSnapshot` does not raise it), so it goes after own video. After a restart everything is foreign and snapshot still goes before video. `makeRoom` runs `freeSnapshot(true)`, `freeVideo(true)`, `freeSnapshot(false)`, `freeVideo(false)`; ownership is filtered by the caller, not by the free helpers.
  - Ownership is the primary key; `StreamUsagePriorities` (index 0 is the highest, §11.2.7.19) orders each side. Ranking first would destroy another controller's idle `LiveView` reservation while an idle `Recording` stream of ours sits untouched; the ranking says nothing about which controller should pay.
  - Do not write down which usage the ranking makes safe: `SetStreamPriorities` (§11.2.8.12) reorders it, and this repo's test fixture ranks LiveView above Recording (the reverse of the spec example).
  - A usage the list does not carry sorts last: destroying what cannot be reasoned about has no way back.
- **The snapshot make-room rung takes any unreferenced snapshot stream whose loss frees capacity.** `freeSnapshotStream` takes an already ownership-filtered list and runs `chooseSnapshotStreamToFree` over it; ownership comes from `ownsSnapshotStream`. That claim requires the lease's allocation record to match the camera's report: a camera reissues freed ids and a never-confirmed lease lives for the process run, so an id match alone can name another controller's stream.
  - `SnapshotStreamDeallocate` refuses on `referenceCount > 0` (§11.2.8.10.2; the reference has no `Internal` case for snapshots), and `CaptureSnapshot` does not raise the count, so a polled stream reads 0. Unreferenced is not unused: a foreign stream taken here may be one another controller polls. It gets `NOT_FOUND` on its next capture and allocates again. Leases do not survive a restart, so this server's own leftover stream reads as foreign after one.
  - A candidate must free an encoder (§11.2.6.13.9) or a share of `MaxEncodedPixelRate` (§11.2.6.13.8) on a camera stating one; otherwise freeing it changes neither the encoder count nor `freeEncodedPixelRate`, and the retry repeats the failed request. Encoder holders first, then size: `MaxConcurrentEncoders` is 1 on the target hardware and a capacity refusal does not say which limit it hit.
  - Registers a restore with the allocation scope, like the video rung. Never runs when `allowEviction` is false. The id does not go in `ResolvedStream.evicted` (video ids only). The ladder keeps its own snapshot list, seeded with the unreported ones, so the re-derived envelope and the exhaustion report describe the camera after the eviction.
- **An evicted stream is announced to every client.** `events.streamEvicted` is emitted where the deallocate succeeds, with a `kind`, so the holder of the vanished id learns it. `video.evicted_stream_ids` on `camera_start_stream` carries video ids only. Do not emit it from `#deallocate` or `releaseStream`: those give back what this server took or what a client asked to release.
- **`allowEviction` gates only the taking rung, and defaults in one place.** `ResolvedStream.evicted` reports the cost. `allow_eviction` defaults to true because reuse, budget and narrowing run first. `false` breaks out before `freeAnUnreferencedVideoStream` and keeps the degraded rung reachable (handing out an existing stream takes nothing). The default lives in `resolveVideoStreamLocked`; `parseStartStreamArgs` leaves it undefined.
- **Ownership decides what this server may deallocate on its own initiative, and nothing else.** `allocatedByUs` means "this process run allocated the stream" and is not persisted; after a restart the device's report is the record. Reuse, adoption and `camera_release_stream` never consult it: `VideoStreamDeallocate` (§11.2.8.7.2) and `AudioStreamDeallocate` (§11.2.8.3.2) refuse only an unknown id, `ReferenceCount > 0` and StreamUsage Internal, and `SnapshotStreamDeallocate` (§11.2.8.10.2) only the first two. An ownership gate on those paths lets one client pin every encoder with unwatched streams and leaves no remedy.
- **The wire folds ownership into `provenance` on `camera_start_stream`: `allocated`, `reused`, `adopted`.** A `reused` flag plus a boolean encoded three states in four combinations. The mapping for existing streams is `existingStreamProvenance` (`CameraStreamManager.ts`). Elsewhere the fact is reported as `allocated_by_server`.
- **Stream usage is not a caller bound.** Reuse and the degraded rung take a stream of any usage, as the camera's own allocate match does. A stream of the session's usage is the first preference, before reference count or size (`usageRank`): §11.2.1.2.1 asks for it, the camera arbitrates resources by the stream's usage (§11.2.1.2.2), and the session gets a stream set up for its purpose. The cost: an idle stream of the session's usage wins over a running one of another usage; whether that costs the camera more encoding work depends on the device. The eviction protection (never free a stream the degraded rung could hand out) covers only another controller's streams. This server's own such streams go last among its own in `makeRoom`; when one was freed and the request still finds nothing, its `FreedVideoRoom.restore` allocates it again and the request hands that out as `degraded`, `allocated`. `restore` runs once, so the scope's give-back reuses its result instead of allocating a second replacement. `ProvideOffer` (§11.5.6.3) does not check the streams' usage, and the privacy modes act on the session's usage, not the stream's. Only a new allocate sends the caller's `streamUsage`.
- **An allocate answer can name a stream that already existed.** The camera answers a request it matches to one of its streams with that stream's id (§11.2.8.1, §11.2.8.4, §11.2.8.8), and its match can be wider than this server's reuse check. An answered id that was reported, or leased and unreported, before the request is handled as a reuse: no `allocated` provenance, no new `allocatedByUs` lease, no give-back on failure, and room the make-room rung freed is not spent, so the scope restores the victim. The restore of a freed stream checks the answer against the reported ids before it leases it. A snapshot stream the adoption capture found gone (NOT_FOUND) is not counted, so the camera reissuing its id is a new allocation. The answered stream is read back from state after the allocate (`*StreamAfterAllocate`; `MatterCameraDeviceIo` re-reads the list), because a reference camera narrows the video range to the request (`UpdateVideoStreamRangeParams`) and matches audio with more channels, a higher sample rate or any bit rate. It must meet the caller's bounds. Otherwise the window search ends (no lease, no deallocate, no further window) and the request goes to the degraded rung with the answered id excluded; 102 `bounds` only when that rung finds nothing. Within the bounds but not the envelope gives `degraded: true` (the reuse predicate). A snapshot match checks the stated codec and stated overlays only, and the captured frame against the ceiling. A stream missing from the fresh read is `SDKStackError`. NOT_FOUND on a deallocate is `gone`: the room is free, nothing is announced or restored.
- **`allocated_by_server` can be wrong, by design.** A lease the camera never confirms has no expiry. On a camera that never reports `Allocated*Streams` the lease list grows one entry per allocation; on one that reports late, a reissued id can match an earlier allocation. Ownership gates the make-room order and the eviction protection, so a stale `allocatedByUs` lease on a reissued id makes another controller's stream count as ours: it is freed earlier, and freed even when the degraded rung could hand it out. A kept snapshot stream on such a camera is not visible in `camera_get_capabilities` but `camera_release_stream` reaches it (it invokes without consulting device state); §11.2.8.8 bounds this to one stream per snapshot capability.
- **Restoring an evicted stream is not an undo.** The camera issues a new `VideoStreamID`; the victim's holder keeps a forgotten id. The restore puts back capacity of that range and usage. No comment may call it an undo.
- **`VideoStreamModify` / `SnapshotStreamModify` are not exposed.** §11.2.8.6 checks only id, state and `Internal`; §11.2.8.11 differs (no `Internal`, plus `DYNAMIC_CONSTRAINT_ERROR` for a capability needing no hardware encoder). Neither checks reference count or allocator, so a modify rewrites a stream other controllers may be watching. A caller wanting different overlays gets a stream of its own.

## Snapshots (`snapshotPolicy.ts`)

- **A snapshot stream outlives its call, and a success always names it in `stream_id`.** Adoption reads `AllocatedSnapshotStreams` fresh each call and takes a stream that meets the caller's bounds and whose smallest possible frame covers the would-be capability per dimension, or, with a `resolution` target, that capability's fitted size in each stated dimension (the camera may answer with any size in the stream's range, §11.2.8.13.3; pixel counts hide aspect-ratio loss). A stale adopted id falls back on the device's own `NOT_FOUND` (§11.2.8.13.3), not on a lease prediction.
- **The snapshot call never deallocates, not even an encoder-holding capability.** The invoke carries no abort and its wait is bounded by `withCleanupBudget` to keep the endpoint lock, so a give-back could expire and still remove the stream later, possibly under a reissued id, making the `stream_id` in the response false. The lease generation guards only this server's record. The failure path's `returnOnFailure` deallocate is safe because that answer names no id. Such a stream pins an encoder until `camera_release_stream` or the video make-room rung frees it; error 103 names it in `allocated`. `encodersExhausted` counts an allocated snapshot stream with `HardwareEncoder` set (§11.2.6.13.9) whatever its reference count, so the next call narrows to what the camera can still serve.
- **The encoder preference orders the ladder, never shortens it.** `selectSnapshotCapabilities` puts encoder-free capabilities first when `encodersExhausted` says all encoders are taken, and keeps the rest behind. The caller's `resolution` target (`orderForTarget`) orders only inside each of those two parts, so a target cannot put an encoder-using capability ahead of the encoder-free one that samples a running video stream. Any rung can be refused with `DynamicConstraintError`, and `encodersExhausted` reads a lagging subscription view, so the device decides. Only the caller's bounds and codec narrow the list; emptying it reports `unsatisfiable`. `bestWithinCallerBounds` is computed before the encoder split, and with a target it is the capability the target selects, which keeps `degraded` from firing when an encoder rung reaches that capability.
- **A `resolution` target selects a capability and shapes the `RequestedResolution`; it never changes what is allocated.** Streams are always allocated at a full capability (`min` = `max`), so they stay reusable by the next caller. `requestedResolution` fits the target into the source actually used (capability or adopted stream) with that source's aspect ratio, never above it. Adoption fits the target to each candidate's own `maxResolution`, as the capture will, and needs the smaller of that fit and the candidate's `minResolution` to reach the capability's fit in every stated dimension. So a larger held stream serves a thumbnail, and a held stream of another aspect ratio serves a width-only or height-only target; the smallest stream that reaches the target comes first. Such a frame is never `degraded` against the capability adoption compared it with; with encoders exhausted that is the first encoder-free one, so a frame can still be `degraded` against the larger `bestWithinCallerBounds`. `isDegradedFrom` with a target compares stated dimensions only (`frame < min(target, capability)` in every stated side): a held stream can have another aspect ratio than the selected capability, and a pixel count against the capability would flag a correct thumbnail.

## Media disposition and tracks (`sdpConstraints.ts`, `CameraStreamManager.ts`)

- **`MediaDisposition` has four states because a nonzero port is not permission to send.** Port 0: `refused`. No section: `absent`. Live section with `a=sendonly` or `a=inactive`: `notReceiving`. Live section the peer receives on: `receiving` — the only state a track may be put into.
  - `mediaRefusal()` takes the whole offer, because an answer carries exactly the offer's m-lines in order (RFC 3264 §6), so `absent` is a refusal; a `SolicitOffer` with no SDP refuses nothing because the camera writes the m-lines. It is the single read path for "may a track of this kind go in the answer"; neither call site decides.
  - `receivableCodecs()` is the single read path for the codec list and answers nothing unless `receiving`. A section with only static payload types states nothing about what the peer decodes (`sdp-transform` builds `media.rtp` from `a=rtpmap` only); narrowing by it refuses callers for a mismatch nobody stated.
  - `sendingAudioSections` is read from the direction before the receiving test, never from the state: `a=sendonly` says "do not send here" and "the peer sends us audio". `withoutTalkback` rewrites exactly those sections, so the two never disagree on which sections send.
  - No direction means `sendrecv` (RFC 4566 §6); a session-level direction applies to every section not restating it (RFC 4566 §5).
  - Refusals are answered where the track is decided, ahead of any narrowing.
  - The Matter spec requires none of this, and the reference camera app ignores the offer's direction (`AddTrack` in `connectedhomeip/examples/camera-app/linux/src/webrtc-libdatachannel.cpp` hardcodes video `SendOnly`, audio `SendRecv`; `webrtc-provider-manager.cpp` parses only `m=`, `a=mid:` and payload types — outside this repo, re-read before relying on it). The reason is this server's use of encoders and reference counts.
- **A track request has three states and one answer site.** `trackRequest(args.video)`: `declined` (`false`), `deferred` (key absent), `demanded` (key present, `{}` included). Resolvers return a `TrackOutcome`; only `CameraStreamManager.resolveTrack` turns "no stream" into a null track or the typed failure. Deciding in the resolvers produced `video: null` with no error for a caller that stated video bounds. The audio resolver reports every dead end as `unavailable`; the video resolver reports only the offer's refusal and throws for the rest, because a camera refusing video is a failed session.

## Sessions (`sessionRegistry.ts`, `controller/webRtcSessionTracking.ts`)

- **What a finished `EndSession` means is decided in one place.** `deviceForgotSession` and `invokeEndSession`: local records go when the device accepts or answers `NotFound` (it does so for any id it cannot resolve — `WebRTCTransportProviderCluster.cpp` `HandleEndSession`, before the delegate), and stay for any other failure so a later stop, disconnect or shutdown still reaches the session. Every route holding a record uses it: `MatterCameraDeviceIo` (requestor tracking), `CameraSessionRegistry.#end` (registry), the raw `device_command` path (requestor tracking, around the registry's own). Do not re-derive the status test at a call site. Only `endSessionWithinBudget` (`webRtcSessionStreams.ts`) bypasses it, because no record names that session yet. The raw `EndSession` does not route through `stopStream`, which fixes the reason to `UserHangUp` and returns a boolean; it goes through `CameraStreamManager.endSessionForClient`, which passes the device's response or error on.
- **The camera's `CurrentSessions` is the record of which sessions exist.** `CameraSessionRegistry` lives for the process run, and only `EndSession` decrements `ReferenceCount`. So `camera_stop_stream` sends `EndSession` for an untracked id instead of answering `ended: false`, and `camera_get_capabilities` reports `sessions` from the device. No ownership gate and no local peer check: `EndSession` (§11.5.6.7.3) fails `NOT_FOUND` unless fabric and `PeerNodeID` match. `CurrentSessions` is fabric-sensitive (§11.5.5.1); `establishedByThisServer` compares `PeerNodeID` with `ControllerCommandHandler.localNodeId`, and foreign entries are still reported because they explain a `referenceCount` a client cannot free. The untracked path is a plain invoke, not a synthesised registry entry. Known gaps: a stop and a `device_command` `EndSession` do not share one `EndSession`, and a reissued id or node removal ends an entry while its `EndSession` is in flight; a later stop by id then sends a second `EndSession`, answered `NOT_FOUND` and reported `ended: false`. An `EndSession` that answers after its id was reissued drops the requestor entry of the new session (the command names only the id); the registry entry ends by report.
- **One lifecycle per session (`CameraSessionRegistry`).** `begin` creates it; `track` makes the same object the tracked entry, so whatever was learned while establishing still counts. Every end goes through it, so a session ends and is announced at most once whatever order reports, stops, releases, peer `End`s, reissued ids and node removal arrive in, and whether an `EndSession` succeeds or fails:

  | Input | Lifecycle effect |
  | --- | --- |
  | `EndSession` (`stop`: `camera_stop_stream`, closing owner, shutdown, all sharing one; `endSession`: `device_command`) | Counted in `endsInFlight` before it is sent. Success: ends with the call's requester. `NotFound`: ends with the camera's recorded end, else the call's. Other failure: nothing; `#settle` runs. |
  | `CurrentSessions` report (`reconcile`) | Records `listed`, or, once listed, the absence as `cameraEnded` (`camera_dropped` / `camera_restarted`). Never discarded. Then `#settle`. |
  | Peer `End` (`peerEnded`) | Records `cameraEnded` `peer`. Then `#settle`. |
  | Reissued id (`issued`, `establishing`) | Ends the tracked entry at once (`camera_restarted`); a registration holding the id is superseded. |
  | Node removal (`forgetNode`) | Ends tracked entries at once (`node_removed`); registrations are marked ended. |

  - `#settle` is the one decision point for a recorded camera end: it ends a tracked session only when no `EndSession` for it is in flight. The first recorded end wins. `#close` is the one place a tracked session ends and is announced.
  - A report that drops a session while an `EndSession` for it is in flight is recorded, not acted on: a finished `EndSession` names who asked, and a failed one leaves the recorded end for `#settle`. A report-ended session is also emitted on `sessionVanished`, from which `MatterController` drops its requestor tracking and stored offer; `EndSession` routes and the peer's `End` drop those themselves.
  - The announcement carries the session's `ownerId` and the cause's `requestedBy` (absent when the server or the camera ended it). The route tells the owner only, never `requestedBy`, which has its own response. An `EndSession` for an id no lifecycle names is announced with no owner ("every camera-aware connection but the asker"), and only when the camera held the session; a `NotFound` for it reports a session neither side had.
  - A registration is not announced to its owner: an end while establishing makes `track` answer `already_ended` (also for a report that listed the id and then no longer did) and the start fails. An `EndSession` that ends a registration is announced with no owner, as for an untracked id.
  - An id the camera hands to a new session drops the entry still holding it (`camera_restarted`) and marks any other registration holding it superseded: the connectedhomeip camera numbers sessions from 0 again after a reboot (static counter in `GenerateSessionId`), and it cannot hand out an id it still holds. `CameraSessionRegistry.issued` does it for every route: `establishing` for `camera_start_stream` (excluding its own registration), `CameraStreamManager.sessionIdIssued` from the raw `send_webrtc_provider_command` route. Without the drop the dead entry wins `signallingOwner` and a later release of its owner sends `EndSession` for the new session. For the same reason a superseded registration is skipped by `signallingOwner` and by every end input, and `track` refuses it with `superseded` ahead of any claim or recorded end; its start then fails without `EndSession` and leaves the requestor entry alone, because both now name the new session.
  - Causes: `other_connection` (`stoppedBy`), `peer` (with the camera's `reason`), `camera_restarted`, `camera_dropped`, `node_removed`, and `released` for the server's own release (closing owner, shutdown, failure give-back), which the route never sends. A new ending needs a cause here and in `CameraSessionEndCause` (ws-client) and the docs table.
  - The peer's `End` reaches `endedByPeer` deferred in `MatterController`, after the `webrtc_callback` emit. The owner also gets the `webrtc_callback` `end`; `camera_session_ended` is the one end event a managed-session client needs.
  - `nodeDecommissioned` reaches `forgetNode`; `WebRtcProviderSessions.nodeRemoved` (from `ControllerCommandHandler.#cleanupNodeAfterRemoval`) drops its requestor sessions and stored offers.
  - Known gap: `batched_device_commands` sends an `EndSession` without the lifecycle; the entry then ends by report or by a later stop answered `NotFound`.
- **WebRTC provider coordination lives in `controller/WebRtcProviderSessions.ts`, not in `ControllerCommandHandler`.** It owns the `CurrentSessions` watch, the callback bridge (stored offers), the establish path (`establishing` wrapper, clock retry) and the requestor records, behind narrow interfaces (`WebRtcProviderNodes`, `WebRtcRequestor`) so it is unit tested with fakes (`WebRtcProviderSessionsTest`). The handler only constructs it and feeds it: bus attribute changes and events, `subscriptionAlive` (`reportCompleted`), `PartsReady` (`endpointAdded`), node removal. `WebRtcProviderDeviceTest` drives the handler's feed and node-state reads against a simulated camera (the device needs `network: { tcp: true }`: the offer commands are large messages).
- **`CurrentSessions` watch (`controller/WebRtcProviderSessionWatch.ts`).** Changes are collected per node and handled at the batch end (`subscriptionAlive`). matter.js applies a report's attribute values and emits its events (also the delayed ones) inside `ClientStructure.mutate`, which `NetworkClient`'s `updated` drains before it emits `subscriptionAlive`, so every change and event of a batch is seen first. Exception: an announcement queued behind a local write's still-open transaction on the same cluster can come later; the provider client is never written. Reboot evidence is the `StartUp` event only: it marks every provider endpoint of the node "restart pending". The mark is used and cleared by the endpoint's first report that comes from a `CurrentSessions` change, and expires after `RESTART_MARK_TIMEOUT` (30 s, `Time.nowUs`), so a StartUp and the emptied `CurrentSessions` in different batches still read as a restart. Batch ends are not counted: `subscriptionAlive` also fires for empty keepalives and on subscription activation (matter.js `NetworkClient`). A report built from node state without a change (first-run sweep, `sweepAgain`, `endpointAdded`) never uses the mark. A later change is not marked, so a genuine drop after a restart reads as `camera_dropped`. A throw from `reported` is logged per endpoint; the mark, the remaining endpoints and the sweep are handled regardless. `CameraSessionRegistry.reconcile` ends a session only after a report listed it (`listed`, per lifecycle, so a reissued id starts unlisted; a registration counts once `establishing` gave it the id): a report built before a new session's offer does not list it. Data versions were not used: they are per cluster, random after a reboot and not exposed through `stateOf`. Unavailability ends nothing. Report-ended entries get their requestor tracking and stored offer removed in `MatterController` (`sessionVanished`); raw-route requestor sessions that vanish are left as they are.
  - Leftover sweep: at the first batch end per endpoint in a process run (the state is then current, from a report or a matching data version), `EndSession` with `UnknownReason` for every entry whose `PeerNodeID` is `localNodeId` that the local requestor does not hold. The requestor holds every session this run opened through `establishWebRtcProviderSession` (both routes; it upserts before it returns), and it does not persist (`CurrentSessions` has no N quality). So the sweep ends sessions from an earlier run and `device_command` `ProvideOffer` / `SolicitOffer` sessions (never in the requestor, so their signalling never worked). `endpointAdded` and `sweepAgain` make a later batch end sweep again; `sweepAgain` comes from `WebRtcProviderSessions.abandon`, for a session a cancelled `camera_start_stream` failed to end (its requestor entry is dropped first, else the sweep would skip it). The sweep is skipped while `establishing` counts an in-flight `ProvideOffer` / `SolicitOffer` on the endpoint, because the camera can report the new session before the answer arrives, and retried at the next batch end. A sweep with an `EndSession` that failed other than `NOT_FOUND` (Busy, timeout) runs again against the then current list at the first batch end `LEFTOVER_SWEEP_RETRY_DELAY` (30 s) later, at most `MAX_FAILED_LEFTOVER_SWEEPS` (3) times in all; then the endpoint is left until `sweepAgain` or node removal, which also reset the count. The bound exists because batch ends include keepalives: an unbounded retry would send an `EndSession` per keepalive to a camera that keeps refusing.
- **Stored offers (`WebRtcCallbackBridge`) are keyed by fabric, peer node, peer endpoint and id.** Ids are unique per node (§11.4.5.1), and matter.js's requestor keys sessions without the endpoint, so the endpoint only matches the address every route uses. A stored offer exists only for an offer the camera accepted and has not answered, of a session still tracked: `offerSent` returns a withdraw function, identity-checked so it never removes a newer offer, which puts back the record it replaced (a re-offer refused while an earlier one waits for its answer). A new session's offer is recorded after the response and before `upsertSession` (the requestor accepts the answer once it holds the session) and withdrawn if the upsert fails. A re-offer's is recorded before the invoke (the session is already tracked, so the answer can arrive first) and withdrawn when the invoke fails or the requestor does not hold the session afterwards. `removeTracked`, `nodeRemoved` and a peer `End` drop it too. `answerWithinOfferedDirections` reads each section's effective direction (own line, else session-level, else `sendrecv`) on both sides and gives a narrowed section a line of its own.
- **The clock push reacts to the camera's refusal; nothing is read before an offer.** `offerWithClockRetry` (`iceServerClock.ts`): only when the camera refuses a `SolicitOffer` (§11.5.6.1.10) or a `ProvideOffer` with a null `WebRTCSessionID` (§11.5.6.3.12) with `INVALID_IN_STATE` and the request carries a `turns:` / `stuns:` URL (`offerChecksClock`), time is pushed once and the same offer is sent once more. The subscribed `UTCTime` cannot decide this: quality `C X` (§11.17.8 table). Do not add a device read before the offer: it costs every offer a request, runs untimed inside the endpoint lock (an offline camera adds MRP timeouts), and a one-shot read with the subscription's fabric filter updates the subscribed data, so every client gets an `attribute_updated`. An accepted offer must cost no extra request. A refused new-session offer ends "with no other side effects", so the retry cannot duplicate a session. When the push fails, the first refusal is thrown; otherwise the retry's. `privacyFailure` maps whichever is thrown.
- **Every camera event goes out through `#announce`, never a bare `emit`.** matter.js `Observable.emit` rethrows an observer's error and returns an observer's promise, so a listener could fail a `camera_stop_stream` that already ended the session, abort a shutdown pass, skip the replacement registration after an eviction, or leave an unhandled rejection. `#announce` uses `MaybePromise.catch` for both.
- **A session that ends before it is tracked is caught by the in-flight registration.** `establishWebRtcProviderSession` upserts the session with the local requestor before it returns. The helper calls `sessionEstablishing` with the answered id before the upsert (the requestor answers `NotFound` for an unstored session, so no `End` can precede it), and `CameraSessionRegistry.establishing` records it. From then on every end input finds the registration by its exact id (`#named`), and `track` answers `"already_ended"` (cause-neutral: peer, report, another stop and another `EndSession` all look the same).
  - Never match on node and endpoint alone: ids are reissued and registrations wait through the endpoint lock, so a loose match refuses sessions other clients just established. After `establishing` no established entry names the id any more, only the pending registration, so every end input for it, including a late `End` of the session that had the id before, refuses the new registration.
- **`webrtc_callback` is routed by owner; an unowned session is broadcast.** `CameraSessionRegistry.signallingOwner` is the only reader of `connectionId` for this, and it also hands the route the owner's `clientSessionKey`. `undefined` (raw-route session or dropped entry) goes to every opted-in connection; withholding it strands a session. An in-flight registration owns its session once `establishing` gave it the id, matched by node, endpoint and that id: the answer and ICE candidates can arrive before `track`. Never match it on node and endpoint alone, which would withhold raw-route signalling while any `camera_start_stream` runs. Do not give the raw route a registry entry (a closing connection would then send `EndSession`). The ended id is dropped in `MatterController` after the emit, because each connection resolves the owner from the entry in its own observer. The node id is branded with `NodeId()` at the route; the registry key is a template string, so a plain number matches only by coincidence.
- **The `webrtc_callback` opt-in happens before dispatch.** `optInToEventsFor` (`WebSocketControllerHandler`) runs first because the camera answers `ProvideOffer` while `camera_start_stream` is in flight; `answer` and early ICE candidates can precede the response. The session's `webrtc_callback` and `camera_session_ended` events are then held per connection (`StartingSessionSignalling`) and sent in `afterResponse`, so the client has the id first. The hold window is the WebSocket handler's, not the registry's pending state: `finish` runs before the response is sent, and an event emitted in between would overtake it. The owner is resolved when the event arrives, not at release, because `MatterController` drops the ended id right after the emit. `afterResponse` runs even when sending the response throws, so a hold always ends. Known gap: the old owner's `camera_stop_stream` or disconnect for a reissued id, sent before it saw the announcement, ends the new session (`stopStream` has no owner check and no endpoint lock). Node `ws` emits every frame of one socket read synchronously, so a Node client resuming from `await` on the response can see the flushed events first; ws-client's `sendCommand` `onResult` runs before the next message. An error response drops the held events: every path that throws after `establishing` sends `EndSession` first (`endSessionWithinBudget`, or `#establishSession` for a session `track` refused), except a `superseded` refusal, whose id names another session. A re-offer (non-null `WebRTCSessionID`, §11.5.6.3) is not a managed command: stream selection sits under `WebRTCSessionID == NULL`, so there is nothing to manage. Docs point to `send_webrtc_provider_command`. For a re-offer, `establishWebRtcProviderSession` skips `sessionEstablishing`, returns the response when the re-offer is untrackable instead of sending `EndSession`, and otherwise calls `upsertSession` with `onlyIfAbsent`: a re-offer without StreamUsage must not end the live session, and one that restates its fields must not overwrite the requestor entry.
- **`client_session_key` is the owner's name for a session, scoped to its connection.** Stored on the registration from `begin` and copied to the entry, so `signallingOwner` and `#close` hand it to the route, which echoes it on `webrtc_callback` and `camera_session_ended` to the owner only. An entry dropped for a reissued id keeps its own key, so the old key is never put on the new session's events. `startStream` refuses a key `clientSessionKeyInUse` (any node, starting or tracked) with error 8 before `begin`, in the same synchronous step, so two starts cannot both take it. `byClientKey` matches connection, key, node and endpoint, and prefers the tracked entry over its registration (both exist between `track` and `finish`).
  - Stop by key while starting: `CameraSessionRegistry.cancel` sets `claimed = "stopped"` (a release claim is kept). The start checks `claimRefusal` (`#throwIfClaimed`) as soon as it holds the endpoint lock, after the video stream, right before the offer, and in `track`. Before the offer it throws error 7, and the allocation scope gives back what the start allocated; a resolution already running (the video ladder, with its evictions) is not interrupted; after, `track` refuses and `#establishSession` sends `EndSession` itself, within the cleanup budget, and hands that outcome to the registry (`ending`), which is what `cancel` answers. A failed `EndSession` rejects the stop, as a stop by id does. When that `EndSession` fails or gets no answer within the cleanup budget, the start's error says which, and `CameraDeviceIo.abandonSession` drops its requestor entry and has the leftover sweep end it at the next batch end; the error never claims an end the camera did not confirm. The answer `cancel` waits on is bounded by the same budget and rejects in both cases, so the stop and the start never disagree. The stop waits for the start, which bounds itself.
  - ICE by key: `StartingSessionSignalling.queueCandidates` takes the newest start with the key (an older one can still be sending its queue after its session ended and the key was reused), and keeps them per start from dispatch until the queue is sent after the response (`release(provide)`), in arrival order. The drain takes every command queued at that moment and sends their candidates in as few `ProvideIceCandidates` invokes as fit one non-TCP Matter message (`MAX_UDP_MESSAGE_SIZE` less a 128-byte reserve, `ICE_CANDIDATES_BYTE_BUDGET`; the cluster states no list or string limit); candidates queued during an invoke go in the next one. A command answers once all its candidates were sent: the first failure among the invokes that carried them, else success. Candidates for an established session are one invoke per command. Before each invoke the drain asks `clientSessionId` (owner connection and key) whether the key still names the start's id; once it does not (the session ended, or a reissued id dropped its entry), the rest of the queue answers error 8, so a delayed send cannot carry the next candidates to another connection's session that got the id afterwards (a new start of the same connection and key that got the same id is not told apart); the start stays findable for candidates until the queue is empty, so a later command cannot overtake. It stops holding events at release regardless. At most `MAX_QUEUED_ICE_CANDIDATES` (64) entries wait; more, an unknown key, and candidates of a start that failed answer error 8 (the camera was never asked, so there is no `NOT_FOUND` status to pass on). Once the start is gone, the key resolves through `clientSessionId` (tracked entries only). Candidates are converted at parse time with a placeholder id that `fieldsFor` replaces, so a bad payload is refused at once.
  - Every claim is refused before allocation and before the offer, so a closing connection's queued start allocates, evicts and offers nothing.
- **Session ownership uses a `bigint` owner id, never the log tag.** `nextConnectionLogTag` is four hex digits and wraps after 0xffff; `nextConnectionOwnerId` never repeats, so `releaseConnection` cannot end another client's sessions after a wrap. Nothing else may key on the tag.
- **A node-scoped event needs its own branch in every client.** The Python client forwards unknown events as `_signal_event(msg.event, msg.data)` with no `node_id`, so per-node subscribers (Home Assistant) never see them. `webrtc_callback`, `camera_session_ended` and `camera_stream_evicted` are in `NODE_SCOPED_CAMERA_EVENTS` (`python_client/matter_server/client/client.py`). Adding to `EventType` only stops the drop.

## Camera API and provider arguments (`webRtcProviderArguments.ts`, `cameraCommands.ts`)

The camera API (seven `camera_*` commands plus two events) does stream management and WebRTC session handling for a client. `send_webrtc_provider_command` and `device_command` with the cluster's own commands stay available for a client doing this itself.

- **One boundary converts a WebSocket payload into provider arguments.** `webRtcProviderArguments.ts`, used by `cameraCommands.ts` (`ice_servers`, `ice_transport_policy`) and `WebSocketControllerHandler.#handleSendWebRtcProviderCommand`. `ControllerCommandHandler` takes matter.js-shaped fields only. The wire uses the W3C `RTCIceServer` shape (`urls`, one URL or a list); `ICEServerStruct` (§11.4.5.3, matter.js field `urls`) takes a list only, so a generic conversion of a single URL fails in the TLV encoder instead of error 8. `WebRtcCallbackBridge` maps back for the `offer` event. `device_command` keeps the cluster's spelling. Do not widen the parsed type to a record or accept a second spelling.
- **Wire keys match fields by `canonicalKey`, not `camelize`.** `canonicalKey` lowercases and drops non-alphanumerics on both sides; it is always at least as wide as `camelize`. `camelize` gets `webrtc_session_id` → `webrtcSessionId` (field is `webRtcSessionId`) and leaves `sdpMLineIndex` (field is `sdpmLineIndex`), and both are spellings this API hands out. Duplicate-key refusal uses the same form. `contractFor` throws at load if two fields of one command or struct share a canonical key. Exception: `ice_servers` entries take the documented keys exactly, since that shape is this API's own.
- **Renaming `ice_servers` on the wire un-masks TURN credentials.** Log redaction keys an ICE server on that member name (separators do not matter; the redactor's `normalize` is `canonicalKey`'s rule).
- **Model-derived conversion; a struct must be named.** `converterFor` builds each check from the `@matter/model` field type and constraint; `contractFor` adds conformance and nullability. `STRUCT_CONVERTERS` is keyed by struct name, not field name. `ICECandidateStruct` converts via `structConverter`; `ICEServerStruct` has a written converter. An unnamed struct-typed field (also via a list) or a scalar type `fieldRange` has no width for throws at module load. `WebSocketControllerHandler` imports this file, so a mismatched model stops the server at startup (as `cameraFieldRanges.ts` does) rather than failing the first offer on a device the operator will blame.
- **`enum8` is bounded by width, not defined values.** Raw-route `streamUsage` takes 0-255 including `Internal` (that route is for clients doing their own allocation); `camera_start_stream` takes a usage by name and refuses `Internal`. `TYPE_MAX` is shared with `CAMERA_FIELD_RANGES`.
- **A caller states streams in one form; the server never picks.** `selectWebRtcStreamFields` refuses `ProvideOffer` / `SolicitOffer` carrying both revision-2 lists and the singular ids: the provider answers INVALID_COMMAND, testing across both media kinds (§11.5.6.1, §11.5.6.3, Effect on Receipt). Refused even on a re-offer, where the device test sits under `WebRTCSessionID == NULL`; nothing a re-offer uses is lost. Dropping one form is wrong: `{ videoStreams: [5], audioStreamId: null }` means video plus auto-selected audio. To a provider not known to be revision 2 (revision 1, or not read yet — it would drop the list and pick streams itself), a single-entry list converts to the singular id (`camera_start_stream` always builds single-entry lists); a longer list is refused, and the refusal says which case. `resolveWebRtcSessionStreams` stays tolerant because its inputs are device data. `originatingEndpointId` is dropped, not refused: `establishWebRtcProviderSession` injects the requestor endpoint.
- **Fields gated on a null session id warn, never refuse.** `contractFor` records per field the fields its conformance compares to null (`nullComparedNames` walks the `Conformance.Ast`: `VideoStreams`, `AudioStreams`, `StreamUsage`, `MetadataEnabled`). `reportFieldsPastTheirGate` logs a warning and forwards unchanged. Three end in a clause that leaves them optional (`[(Rev >= v2) & (WebRTCSessionID == NULL)].d+, O`); `MetadataEnabled` (`METADATA & (WebRTCSessionID == NULL)`) has none but is forwarded because what the device does with it is its answer. `OriginatingEndpointID` is not covered (dropped earlier). No refusal or drop without a spec line saying the device refuses it.
- **Four relayed provider commands; two establish a session.** `establishesWebRtcSession` decides; `WebSocketControllerHandler` calls `invokeWebRtcProviderCommand` (establishing pair only, by signature) or `invokeWebRtcSignallingCommand` (`ProvideAnswer`, `ProvideIceCandidates`; plain invoke, `null` result, name from `SIGNALLING_INVOKE_NAMES`, a `Record` so an unmapped name does not compile). The split is at the WebSocket route. `WebRtcProviderDeviceTest` constructs a real `ControllerCommandHandler` and drives `invokeWebRtcProviderCommand` against a simulated camera, so handler branches are testable there. Signalling commands carry no `originatingEndpointId` and have no response, so they must not take the establish path. `EndSession` is not on the list; `camera_stop_stream` owns it.
- **`camera_provide_answer` and `camera_provide_ice_candidates` complete a managed session** (including `mode: "solicit_offer"`, whose offer arrives on `webrtc_callback`). `parseSignallingArgs` (answer) checks the object and key set, drops `node_id` / `endpoint_id`, and hands the rest to `toProviderCommandFields`; no second conversion. `parseIceCandidatesArgs` does the same for the candidates after taking the session reference (id or `client_session_key`, exactly one). The route adds only `subjectName` so refusals name the camera command. No session check against local records: the camera's `PeerNodeID` and fabric test decides. Ownership decides who receives signalling, never who may send it.

## Wire argument checks (`WebSocketControllerHandler.ts`, `cameraCommands.ts`, `cameraFieldRanges.ts`)

- **`args` is decided once at dispatch.** `commandArguments` substitutes `{}` for missing or null `args` (the Python Matter Server's reading: `parse_arguments` in `matter_server/common/helpers/api.py`) and refuses non-objects with error 8. That refusal is stricter than the reference, which fails on a non-dict `args` while decoding `CommandMessage` with an `AttributeError` its `except ValueError` does not catch, and closes the connection without an answer (read and run in that project's checkout, not here). The shape is checked before the command lookup, so unknown command plus bad `args` answers 8, not 9; a non-string command skips the check and answers 9. No per-command shape check; required arguments stay each command's own (a missing `node_id` on a node-targeted generic command still reaches `NodeId()` and answers 0; `read`, `subscribe` and `unsubscribe` answer 8 through `toNodeIdValue`).
- **Camera command shape and keys are checked where the target is parsed.** `parseCameraCommand` refuses non-object `args` before the key check (`Object.keys` reads a string's indices) and returns the fields, so parsers take `unknown` and read only from that. It refuses keys outside the command's set; `CAMERA_ARG_KEYS` is the only pairing of command name and key set, each a `Record` over `ArgsOf<>` so an unlisted wire argument does not compile. `send_webrtc_provider_command` uses the same `requireArgumentObject` and `parseTargetIds`. Nested objects check their own keys: `video` / `audio` hints, `ice_servers` entries, and resolutions (a `{ width, height, frame_rate }` would state a bound nothing reads).
- **Wire numbers are bounded per field from `@matter/model`.** `cameraFieldRanges.ts` reads the constraint, falling back to the TLV width. Past the width a value hits matter.js's TLV encoder instead of error 8, and for `camera_stop_stream` an out-of-range `webrtc_session_id` answered `ended: false`, which reads as an already-ended session. Ids are bounded from the command fields they become (`EndSession.WebRtcSessionId`, the three `*StreamDeallocate` fields), so future constraints are picked up. `isInRange` requires a plain safe-integer number inside the field's uint16 range.
- **`node_id` is bounded in `toNodeIdValue` (`src/camera/wireArgumentChecks.ts`), because `NodeId(v)` is `BigInt(v)` and validates nothing.** Shared by the camera `parseTargetIds` and `read` / `subscribe` / `unsubscribe` (`#interactionNodeId`). Otherwise a negative id reaches the node lookup and answers `NODE_NOT_EXISTS`. Bigints are bounded by matter.js `UINT64_MAX` (Core §2.5.5). Numbers must be safe integers (`9.007199254740993e15` arrives as ...992); `parseBigIntAwareJson` turns large plain literals into bigints, so an unsafe number here is an exponent-form literal. `nodeIdTarget` then refuses every class that is not one node (group, Null Group, Unspecified, CAT, PAKE, reserved). `endpoint_id`'s `0xfffe` is a literal. `device_command` does not go through here; it uses `#targetNodeIdOrGroup`.

## Logging and redaction (`@matter-server/ws-client`)

- **Requests are logged before validation, so redaction is by shape, not by command.** `redactSensitiveCommandFields` walks `args` and masks an explicit name list, matched whole with case and separators removed (`setup_pin_code`, `setupPinCode`, `PINCode`). Whole-name matching keeps KeypadInput's `keyCode` visible.
  - Its `normalize` duplicates `canonicalKey` (ws-client does not depend on this package) and must stay at least as wide as any rule the server matches keys with.
  - Masked anywhere: setup codes and passcodes, Wi-Fi passphrases, Thread datasets, symmetric key material. The list was checked against `@matter/model` for names that carry nothing else.
  - `username` / `credential` are masked only inside an entry under a member naming a list of ICE servers (`ice_servers`, `ICEServers`, via the same `normalize`), keeping the Door Lock `credential` struct readable. Keyed on path, not on a `urls` sibling, so an entry the server is about to refuse for having no URL is still masked.
  - Only requests are walked; nothing masks responses except `skipMessageContentInLogFor`, which drops the whole payload (`camera_snapshot`, `open_commissioning_window`, plus `start_listening`, `get_network_topology`).
  - A new argument that can carry a secret is masked here, not at its command. Everything else is logged unchanged on purpose.
- **Incoming messages: `redactIncomingMessage`.** Masks `a=ice-ufrag`, `a=ice-pwd` and ICE server `username` / `credential` anywhere under a message down to `MAX_DEPTH` (deeper content is kept, so `start_listening` stays readable). A string past 1024 characters is replaced by its length, which keeps a `camera_snapshot` frame out of the console without a command-keyed rule (responses name no command); the rule reaches bare array entries too. An `sdp` is handled by the member rule first and keeps its lines. The DTLS fingerprint is not masked (public binding, not a secret). The field-name list is not applied to incoming messages. Outgoing arguments are logged at any length.

## Features, privacy, overlays

- **A refusal may name only a device fact the report carries.** `camera_get_capabilities` reports the AVSM `FeatureMap` as `features` (via `globalsOf(CameraAvStreamManagementClient).featureMap`; `stateOf` omits it) and the three privacy attributes as `privacy`.
  - A demanded track on a camera lacking the feature fails 102 `reason: "feature"` with `feature` from `featureName()` (the model's feature key). A deferred track resolves to absent through `resolveTrack`.
  - The offer's refusal is tested first, so a demanded video track with no video section answers without `feature`.
  - The video gate is at the call site (the video resolver throws); the audio gate is in `resolveAudioStreamLocked`. The snapshot gate is ahead of the capability ladder, since a camera without the feature may still list capabilities and would get a `SnapshotStreamAllocate` its `AcceptedCommandList` lacks.
  - `lacksFeature` is the one read path and answers false for a feature map not yet arrived: matter.js defaults the map until the device reports, and one of Audio, Video, Snapshot is mandatory (§11.2.5). Reading "not arrived" as "no video" strands a real camera in audio-only. An unreadable map (raw bitmap) also gates nothing.
  - `statedFeatureNames` uses the same test, so `features` is absent (not empty) for such a camera. Names come from the map and spelling from `CameraAvStreamManagement.Feature`; an unnamed flag is reported under its flag name, sorted last.
  - `hdrCapable` comes from the feature map, because `HDRModeEnabled`'s presence cannot tell "no feature" from "not arrived".
- **Privacy is never pre-checked; `privacyFailure` maps a device rejection.** Only `INVALID_IN_STATE` from the provider (§11.5.6.1.10, §11.5.6.3.12) or `CaptureSnapshot` (§11.2.8.13.3), and only when a reported switch covers the call; the same status also means other things (a `turns:` ICE server with null `UTCTime`), so otherwise the device error stands. Allocates and deallocates are excluded: `VideoStreamAllocate` (§11.2.8.4.12), `AudioStreamAllocate` (§11.2.8.1.7) and the deallocates use `INVALID_IN_STATE` for usage and reference-count cases, and privacy is not in their Effect on Receipt. A pre-check on a stale "on" would leave no path to the device. State is re-read inside `privacyFailure`. Coverage: soft livestream → `LiveView`; soft recording → `Recording`, `Analysis`; snapshot → hard switch and livestream. Tests cover both directions. `modes` lists every forbidding switch with no order claimed. Error 106, not a 102 reason, because asking for something else cannot fix it.
- **Overlay flags: one policy in `overlayPolicy.ts`.** `WatermarkEnabled` / `OSDEnabled` are conformance `WMARK` / `OSD` on `VideoStreamAllocate` (§11.2.8.4) and `SnapshotStreamAllocate` (§11.2.8.8); the reference enforces a biconditional (`HasFeature(Feature::kWatermark) == commandData.watermarkEnabled.HasValue()`, `INVALID_COMMAND` either way), which `ladderReaction` rethrows. `resolveOverlays` turns the caller's statement plus `overlaySupport(state.features)` into fields. Rules decided there only:
  - An unstated overlay goes out as `false` on a camera with the feature (§11.2.6.11 gives both `VideoStreamStruct` fields a fallback of 0).
  - On a camera without the feature, stated `false` is met by sending nothing; stated `true` is 102 `reason: "feature"` with `feature`.
  - An unstated feature map gates nothing: the caller's statement goes to the device, silence sends nothing. The biconditional holds only for a camera that has answered.
  - A stream's absent flag reads as off only in `overlaysMatch`; elsewhere absence means "must not go on an allocate". The wire boundary (`toWireCapabilities`, `toWireStartStreamVideo`) is the only other `?? false`.
  - `AllocatedVideoStream.overlays` keeps the camera's own optionality unchanged, which makes it the honest report for reuse/degraded and a conformant request for `#restoreFreedVideoStream`. Deriving the restore from the feature map drops overlays while the map is unstated.
  - A stated flag is a caller bound: `satisfiesVideoCallerBounds` holds it at the reuse and degraded rungs, and the allocate rungs send it through `envelope.overlays` (from `resolveOverlays`). An unstated flag resolves to `false` on the envelope (checked by `fitsPlan` through `overlaysMatch`), so the degraded rung may give it up with `degraded: true`. Moving it into caller bounds makes degraded unreachable; dropping it from the envelope gives identical calls different pictures.
  - Known limits, documented not coded around: the reference dedup (`UpdateVideoStreamRangeParams`) ignores overlays, so a returned existing id keeps its overlays; §11.2.8.8.6 lets a camera ignore both fields on a snapshot capability with `RequiresHardwareEncoder` false. That is logged only; the effect is that `findAdoptableSnapshotStream` stops adopting and each call re-allocates, which §11.2.8.8 dedups to the same id.

## Releasing a stream

- **`releaseStream` always sends the deallocate; the cached reference count never gates it.** It raises error 104 (`ServerError.cameraStreamInUse`) only on the camera's `INVALID_IN_STATE`, keeping the device error as the cause (the reference answers that status only for a reference count above 0 and passes its delegate's status through). The cached count only fills in `reference_count`. A stale cached count is wrong in both directions, so do not put it back in front of the invoke.
