# WebSocket API Schema Changelog

The server advertises a `schema_version` in its `server_info` on connect. Clients gate
version-dependent commands/fields with `require_schema`, and the server keeps supporting a
minimum schema so older clients keep working. This page tracks, per schema version, which
commands, arguments, events, and wire fields were added or changed — so client authors can
see exactly what a given schema level provides.

The server-side constants live in `packages/ws-controller/src/server/WebSocketControllerHandler.ts`
(`SCHEMA_VERSION`, `MIN_SUPPORTED_SCHEMA_VERSION`). Versions predating this document are not
listed retroactively; entries start at the first version maintained here.

## Schema 14

Minimum supported: 11 (older clients keep working with the pre-14 command shapes).

### Camera stream management

- **Five new commands** — `camera_get_capabilities`, `camera_start_stream`, `camera_stop_stream`, `camera_snapshot`, `camera_release_stream` — move Matter camera stream setup into the server. It computes the `VideoStreamAllocate` envelope, reuses or allocates video and audio streams, reacts to the device's rejections, and tracks the WebRTC session per node, endpoint and session id, ending it when the connection closes. Clients detect the commands via `server_info.schema_version >= 14`. The raw `send_webrtc_provider_command` / `device_command` path keeps working for a client doing its own allocation; `send_webrtc_provider_command` gained the argument contract described below.
- **`camera_get_capabilities`** reports only device-stated facts: `video` (`sensor`, `min_viewport`, `max_fps`, `max_hdr_fps`, `hdr_capable`, `rate_distortion_points`, `codecs`), `audio` (`codecs`, `channels`, `sample_rates`, `bit_depths`, `two_way_talk_support`), `snapshot.capabilities`, `limits` (`max_encoded_pixel_rate`, `max_concurrent_encoders`, `max_network_bandwidth`, `supported_stream_usages`, `stream_usage_priorities`) and `allocated` streams per kind, each with `reference_count` and `owned_by_server`. `allocated.snapshot[]` reports `min_resolution` and `max_resolution` separately, as `SnapshotStreamAllocate` stated them, because a snapshot stream is allocated for a range and the device picks a frame size inside it; streams this server allocates carry one capability resolution as both bounds. There is deliberately **no resolution list** — the camera does not state one, and a derived list offers resolutions it cannot serve. `video.codecs` is derived from `rate_distortion_points`, so a camera that states no trade-off point reports an empty list.
- **`camera_get_capabilities` also reports `sessions`**, the camera's own `CurrentSessions` list: each entry carries `webrtc_session_id`, `peer_node_id`, `peer_endpoint_id`, `stream_usage`, `video_stream_ids`, `audio_stream_ids` and `established_by_this_server`. That list is what holds an allocation's `reference_count` above zero, and it is the only place a session id can be learned after the server restarted, since the server tracks sessions in memory only. `camera_stop_stream` accepts an id from it whether or not this server established the session in its current run, so a session left open by an ungraceful restart can be ended and its streams released. The attribute is fabric-sensitive, so only this fabric's sessions appear; `established_by_this_server` says the camera recorded this server as the peer, which is exactly when the camera accepts an `EndSession` for it.
- **`camera_start_stream`** takes `stream_usage` plus optional `sdp`, `video`, `audio`, `ice_servers`, `ice_transport_policy` and `metadata_enabled`. An `ice_servers` entry is `{ urls, username?, credential?, caid? }`, with `urls` one URL string or a list of up to 10; the server translates it into the cluster's `ICEServerStruct`, whose field is `URLs` and always a list, and refuses an unknown key, an entry naming no URL or a value past the struct's limits with error 8. `video` hints are ranges (`codecs`, `min_resolution`, `max_resolution`, `min_frame_rate`, `max_frame_rate`, `min_bit_rate`, `max_bit_rate`); `audio` hints are exact values (`codecs`, `channel_count`, `sample_rate`, `bit_rate`). Any other key under a hint object is refused with error 8, and so is any other top-level argument. Every bound the caller states is hard in both directions: nothing is widened, lowered, clamped or swapped for another codec to make a request fit. `video` and `audio` each make one of three statements: present (an object, `{}` included) asks for the track, `false` declines it, left out leaves it to the server. A track that was asked for and cannot be resolved fails the call instead of answering `null` for it: error 102 when no capability, codec or range fits, error 103 when the camera refused the allocation for lack of capacity, or error 7 when the device accepts the allocation but returns no stream id. A device status the allocation ladder does not recognize is not translated into one of those codes; it surfaces as error 0 instead. A request that leaves both tracks out — `video: false` with `audio: false`, or `video: false` with no audio stream resolved for a caller that left `audio` to the server — fails with error 102 (`reason: "capability"`, `device` and `requested` both empty) instead of sending an offer with neither track. A media section the `sdp` rejects (`m=` line with port 0) is the peer declining that kind, and so is a section it states `a=sendonly` or `a=inactive` on, or no section of that kind at all: no track of it is put in the answer, and a caller that asked for that track is told with error 102 (`reason: "capability"`, `track` naming it) rather than handed a stream. A call without `sdp` refuses no kind, because the camera writes the offer itself. An `a=fmtp` limit narrows only the codec that stated it, and binds every rung, including the degraded one. The codec's own level is such a limit: `profile-level-id` (H.264) and `level-id` (H.265) are mapped through the codec level tables, the codec's own capability parameters override the level's value — `max-fs` / `max-mbps` for H.264, `max-lps` / `max-lsr` for H.265, never each other's — and a codec whose stated level the server cannot map is not selectable — a request left with no selectable codec fails with error 102 and `reason: "level"`.
  - The response is `{ webrtc_session_id, mode, video, audio }`. Each track reports `stream_id`, `codec`, its allocated values, `reused` and `allocated_by_server`; `video` also reports `degraded: true` when the stream does not fit the range the server computed while still meeting every bound the caller stated. `stream_id` is the id `camera_release_stream` takes.
- **`camera_snapshot`** takes optional `max_resolution` and `codec`; any other argument is refused with error 8, the same as an unknown hint key on `camera_start_stream`. It returns `{ data, codec, resolution, downgraded, stream_id }`. `data` is base64 image bytes and `downgraded` says the frame is smaller than the best capability the request's own bounds allowed. `stream_id` names the snapshot stream the frame came from, which a successful call always leaves on the camera, so it is the id `camera_release_stream` takes. The call captures from a snapshot stream the camera already has whenever one fits the request's bounds and is no smaller than the capability it would otherwise allocate, whoever allocated it; a stream it does allocate stays for the next call, whatever capability it came from. A stream allocated at a capability that requires the hardware encoder holds one of `max_concurrent_encoders` while it exists, so on single-encoder hardware a later `camera_start_stream` fails with error 103 until the client releases it.
- **`send_webrtc_provider_command` refuses a `ProvideOffer` / `SolicitOffer` payload that states both stream forms.** The `videoStreams` / `audioStreams` lists and the `videoStreamId` / `audioStreamId` they deprecate cannot be sent together — a camera fails such a command with `INVALID_COMMAND`, across both media kinds — so the payload is refused with error 8 rather than one form being dropped. A list is sent as stated to a camera at cluster revision 2; to one below it, or one whose revision this server has not read, a single-entry list is converted to the singular id and any other length is refused, instead of being cut down to its first entry. An empty list is refused at every revision, since the field takes 1 to 16 entries.
- **Every command requires `args` to be an object when it states one.** A message that leaves `args` out, or sends `null`, carries an empty argument set: a command whose arguments are all optional answers it, and one with a required argument refuses it the way it refuses that argument being absent. An `args` that is a string, a number, a boolean or an array is refused with error 8 naming the command, instead of a handler destructuring a shape that was never an argument object and the throw being reported as error 0. The rule is at the dispatch and is not gated on schema 14: it is how every command on every schema level reads its arguments. Unknown argument keys are the one place the two servers differ on purpose — the Python Matter Server ignores them, while the five camera commands and `send_webrtc_provider_command` refuse them with error 8.
- **`camera_get_capabilities`'s `allocated.snapshot[]` entries carry `hardware_encoder`**, the camera's own statement that the stream uses one of its `max_concurrent_encoders`. Such a stream holds that encoder while it exists, whatever its `reference_count`, and nothing but `camera_release_stream` frees it, so it is what a client releases on error 103. Error 103's `allocated` list names those snapshot streams beside the referenced video streams.
- **`camera_release_stream`** takes `kind` (`"video"`, `"audio"` or `"snapshot"`) and `stream_id`. Every stream id and `camera_stop_stream`'s `webrtc_session_id` are uint16, so a value above 65535 is refused with error 8 instead of being reported as a stream or session the camera does not have. It deallocates on the camera's terms rather than the server's: the cluster protects a stream by its reference count and by the `Internal` stream usage and checks neither the allocator nor the fabric, so the stream need not be one this server allocated. The camera's own `INVALID_IN_STATE` becomes error 104; the reference count the server last read decides nothing and only fills in `reference_count` in the detail when it is above zero. A missing AV Stream Management cluster is still 106 and a malformed argument still 8, and everything else is the device's answer. `owned_by_server` on `camera_get_capabilities` says only that this server allocated the stream during its current run, which decides what it may deallocate unasked.
- **Codecs and stream usages are names, not numbers, in both directions.** `H264`, `H265`, `H266`, `AV1`, `OPUS`, `AAC`, `JPEG`, `HEIC` — the SDP spelling of the cluster enum — on `video.codecs`, `rate_distortion_points[].codec`, `audio.codecs`, `image_codec`, the allocated streams' `video_codec` / `audio_codec` / `image_codec`, a started stream's `codec`, a snapshot's `codec` and the `device` / `requested` lists on error 102. `two_way_talk_support` is a name as well (`NotSupported`, `HalfDuplex`, `FullDuplex`), and so are the stream usages: `supported_stream_usages`, `stream_usage_priorities` and an allocated stream's `stream_usage` report `Internal`, `Recording`, `Analysis` and `LiveView`. A codec value the cluster enum does not define is reported as its decimal digits and accepted back in that spelling, because a camera may use a codec this build does not name. The stream usages are a closed set: a value the enum does not define is reported by number and cannot be requested.
- **A name round-trips; a key does not always.** `video.codecs`, `audio.codecs` and `snapshot.capabilities[].image_codec` are sent back under the same names. `audio.channels` is the ceiling for the `audio.channel_count` hint, `audio.sample_rates` the set the `audio.sample_rate` hint must name, and `limits.supported_stream_usages` supplies `stream_usage` — except `Internal`, which `camera_start_stream` refuses because it marks a stream the device keeps for itself. `audio.bit_depths` has no hint at all.
- **`send_webrtc_provider_command` takes the documented `ice_servers` shape, and checks every field.** Its `payload` reaches the same `ProvideOffer` / `SolicitOffer` arguments `camera_start_stream` builds, through the same boundary, so an `ice_servers` entry is `{ urls, username?, credential?, caid? }` on both commands and on the `webrtc_callback` `offer` event. Before this the raw route converted field names generically and knew nothing of the struct, so the documented entry reached the TLV encoder with the mandatory `URLs` unset and failed there. Every other field is now checked against the cluster's own definition as well: numbers against the range their field encodes in, strings against the ceiling their field states (`sdp` states none and takes any string), lists against the entry count their field takes, and mandatory fields for being present. A failure is error 8 naming the key as sent. Payloads that worked before and are now refused: a key naming no field of the command, a second key resolving to a field another already filled (matter.js dropped what it could not place and a duplicate overwrote silently, so the caller got a session it did not ask for), a payload omitting a mandatory field, a payload that is not an object, and an ICE server spelled in the cluster's own `URLs` rather than the documented `urls`. `originatingEndpointId` is dropped rather than checked, because the server injects its own. The generic `device_command` route is unchanged: it serves every cluster and keeps taking each payload in that cluster's own field names, and it establishes no session — a provider command sent that way is a bare invoke.
- **`send_webrtc_provider_command` also relays `ProvideIceCandidates`,** so a client has a checked route for trickled ICE candidates. Before this the command was the two session-establishing ones only, and a candidate could reach a camera only through the generic `device_command`, in the cluster's own field names. `ProvideOffer` and `SolicitOffer` still establish a session — originating endpoint, stream-field reconciliation against the camera's cluster revision, registration with the local requestor — while `ProvideIceCandidates` signals for a session the camera already holds, establishes nothing and answers `null`, because the cluster defines no response payload for it. An `ice_candidates` entry is `{ candidate, sdpMid, sdpMLineIndex }`, exactly what the `webrtc_callback` `ice_candidates` event reports.
- **A payload key is matched to a field with case and the separators between words ignored, not by `camelize`.** `camelize` read `webrtc_session_id` — the spelling every other command in this API uses for that id — as one word and resolved it to no field, and left the W3C `sdpMLineIndex` unchanged where the cluster's field is `SDPMLineIndex`; both are spellings this API hands a client, and both were refused as unknown keys. The accepted spellings are therefore wider than before, never narrower, and the duplicate-key refusal covers them: `{ webrtc_session_id, webRtcSessionId }` in one payload is refused rather than one of them silently winning.
- **`send_webrtc_provider_command` refuses an argument of its own that it does not take**, as its payload already refused a key naming no field.
- **A `ProvideOffer` re-offer that states new-session fields is forwarded, and logged.** `videoStreams`, `audioStreams`, `streamUsage` and `metadataEnabled` are the fields the cluster states for a request whose `WebRTCSessionID` is null; a provider's Effect on Receipt runs its whole stream-selection step under that condition, so on a re-offer they change nothing and the response reports nothing about them. Such a payload is sent as stated — the camera decides what a field it did not ask for means — and the server writes a warning naming the command, the session id and the fields, since nothing else makes the mismatch visible. The fields are read from their own conformance in the Matter model rather than listed, so a field the model gates the same way is covered too — except `originatingEndpointId`, which this command drops before the check because the server injects its own.
- **All five camera commands refuse an argument key they do not know**, with error 8 naming the key and listing the ones the command takes. A dropped key would answer a request the client did not make, which is the one thing these commands never do with a stated argument. The check is in the target parse every one of them runs, so it covers `camera_get_capabilities`, `camera_stop_stream` and `camera_release_stream` as well as the hint-carrying two.
- **New error codes 102, 103, 104 and 106** — `CameraStreamIncompatible`, `CameraResourceExhausted`, `CameraStreamInUse`, `CameraNotSupported` (OHF extensions; python-matter-server codes stop at 11). Error 102 carries `reason: "codec" | "bounds" | "capability" | "level"` and, for a failure about one track, `track: "video" | "audio"`. `capability` covers two different cases, which `track` tells apart: a track the caller asked for cannot exist — the device states no capability of that kind, or the offer rejects that media section, and no different request can succeed — and a `camera_start_stream` request that leaves both tracks out entirely, reported with no `track` and `device`/`requested` both empty, which is fixed by asking for at least one track. `level` names an offer whose every shared codec states a level the server cannot map to the codec level tables. It also carries `bound: { field, requested, limit }` when the server ruled a caller bound out before asking the device, and `device_status` when a device rejection produced it. `bound.field` is the hint key as the wire spells it: `min_resolution`, `min_frame_rate`, `min_bit_rate`, `sample_rate` or `channel_count`. Error 103's `allocated` entries carry a `kind`, because the streams holding the capacity are not always the kind that was asked for. Error 106's `missing_clusters` names the cluster ids the endpoint does not expose. `camera_start_stream` raises 106 when either cluster is missing; `camera_get_capabilities`, `camera_snapshot` and `camera_release_stream` raise it only when the AV Stream Management cluster itself is missing.

## Schema 13

Minimum supported: 11 (older clients keep working with the pre-13 command shapes).

### Network topology

- **New command `get_network_topology`** → a `NetworkTopology` (`{ collected_at, nodes[], connections[] }`) describing the whole Matter network as a graph: the Thread mesh (nodes + neighbor/route-table links, with external neighbors and mDNS-discovered Border Routers) and the Wi-Fi star (one `wifi_ap` pseudo-node per BSSID — id `ap_<BSSID>` with colons stripped, e.g. `ap_112233445566` — stations linked to it). Ethernet nodes appear unlinked. Optional `refresh` argument re-reads the Thread neighbor/route tables, routing role and network name (and Wi-Fi diagnostics) from every online node before building the snapshot (slower — seconds; best-effort, concurrency-capped, under an overall deadline, and shared between concurrent requesters); omitted/`false` builds from the current attribute cache.
  - Node kinds: `matter` (commissioned here; carries `node_id`), `border_router`, `thread_unknown` (a neighbour not commissioned on this fabric), `wifi_ap`. Thread connections keep both observed directions (`source_to_target` / `target_to_source`) so asymmetric links stay legible; the top-level `strength` is the strongest observed direction. `strength` values are `strong` / `medium` / `weak` / `none` / `unknown` — `none` means the link was observed dead (Thread pairs with no live direction are omitted entirely), `unknown` means no measurement was available (e.g. a Wi-Fi station whose RSSI can't be read) and must not be rendered as a dead link. Border Router classification depends on mDNS discovery: when the server runs with Thread diagnostics disabled, no `border_router` nodes appear and every external neighbour is reported as `thread_unknown`.
- **New event `network_topology_updated`** → a `NetworkTopology`, emitted (debounced, latest-wins coalesced) whenever the derived graph changes, plus a slow periodic refresh so sleepy-device drift is eventually reflected. **Delivered only to connections that have issued `get_network_topology`** during their lifetime — mirroring the schema-12 `thread_diagnostics_updated` opt-in so pre-schema-13 clients never receive an event type they didn't subscribe to. **Outgoing events carry no `require_schema`**; clients detect support via `server_info.schema_version >= 13`.
- **`host_name` on `border_router` nodes** (added after 1.4.0 shipped schema 13, so there is **no version signal** for it — treat it as presence-detectable only). The Border Router's mDNS host name as a *display label*, not an address: the trailing dot and a `.local` suffix are stripped (`"Cuisine.local."` -> `"Cuisine"`). Several vendors report an identical `vendor_name`/`model_name` pair for every unit they ship, which renders a multi-BR network as a row of identical labels; prefer `host_name` when present and keep the `vendor_name`/`model_name` fallback, which is permanent — the field is absent both on older servers and whenever a Border Router's `_meshcop` SRV host name was never resolved. The raw FQDN remains available verbatim via the schema-12 `get_thread_border_routers`.
- **`ssid` / `bssid` on Wi-Fi nodes** (also added after 1.4.0, presence-detectable only). Both are set on `wifi_ap` nodes and on the `matter` stations joined to them — stations previously carried no network identity at all. `bssid` is the radio address that `network_name` already carries on `wifi_ap` nodes, now under a self-describing name; `network_name` keeps its old value there so existing consumers are unaffected, and is superseded for Wi-Fi. `ssid` comes from NetworkCommissioning (`0/49/1`), whose `networkID` is the SSID only for Wi-Fi — it is the extended PAN id for Thread and the interface name for Ethernet — and some devices leave it empty, so a `bssid` fallback stays necessary. Note that one BSSID is one AP radio: a mesh reports several `wifi_ap` nodes sharing an `ssid`.

See `packages/ws-client/src/models/model.ts` for the exact `NetworkTopology` / `NetworkTopologyNode` /
`NetworkTopologyConnection` wire shapes (each field documented inline).

> This first iteration derives Thread links from the nodes' own `ThreadNetworkDiagnostics` (neighbor +
> route tables) and classifies externals against the passively-discovered Border Router registry. The
> richer MeshCoP diagnostic enrichment (route64 / childTable → router-to-router links and
> diagnostic-only mesh nodes) is a planned follow-up; the wire model already accommodates it.

### OTA firmware upload

- **New command `initiate_ota_upload`** (no arguments) → `{ upload_id, expires_in, max_size }`. Authorizes exactly one upload of a local `.ota` firmware image and claims one of the server's limited in-flight upload slots. `upload_id` is a random 32-hex string, single-use, bound to the client that reserved it, and valid for `expires_in` seconds — that window bounds when the following POST may *start*; the transfer itself is bounded by `max_size` (bytes), not by time. Fails with `OtaUploadError` (101) when OTA support is disabled (`--disable-ota`) or all slots are taken (`--ota-upload-max-in-flight`, default 5).
- **New HTTP endpoint `POST /ota-upload/<upload_id>`** on the same listener as `/ws` — not a WebSocket command, so a firmware image neither pays the ~33% base64 overhead nor has to be buffered whole in memory. Body is the raw `.ota` bytes. Answers `200` with a `MatterSoftwareVersion` (`update_source: "local"`), `400` `{ error_code, message }` for a corrupt image / unknown / expired / already-used / foreign-client id, `404` for a malformed id, `413` when the image exceeds `max_size` (`--ota-upload-max-size-mb`, default 64). The reservation and the staged file are always discarded before the response is sent, success or failure.
- **New error code `OtaUploadError` = 101** (OHF extension; python-matter-server codes stop at 11).
- Stored images are indexed by the vendor ID / product ID / software version in their header, not against a node: `check_node_update` surfaces one for any node whose vendor/product matches (its cached answer for that vendor/product is dropped on upload). *Test* images are only served when the server also runs with `--enable-test-net-dcl`, the same restriction that applies to `--ota-provider-dir`.
- **Clients detect support via `server_info.schema_version >= 13`** — the endpoint is unavailable both on older servers and when OTA is disabled.

## Schema 12

Minimum supported: 11 (older clients keep working with the pre-12 command shapes).

### Credentials — named credential lists

- **New command `get_all_credentials`** → `{ wifi: { id, ssid }[], thread: { id, networkName, extPanId }[] }` (summaries only; secrets stay write-only and are never returned).
- **Optional `id` argument** on `set_wifi_credentials`, `set_thread_dataset`, `remove_wifi_credentials`, `remove_thread_dataset`. Omitted → the reserved `default` entry (backward-compatible with pre-12 callers).
- **`wifi_credentials_id` / `thread_dataset_id`** arguments on `commission_with_code`, selecting which stored credential to use.
- **`set_wifi_credentials` blank-password semantics.** A password is required on set; an empty `credentials` is accepted only to keep the stored (write-only) password when the `ssid` is unchanged (re-saving an entry without resending the secret). A blank credential with a new/changed SSID — or on a first set with nothing to keep — is rejected (`invalid_arguments`), so the old secret is never re-paired with a different network. To clear an entry — including the reserved `default` — use `remove_wifi_credentials` / `remove_thread_dataset`, which zeroes both the SSID and the secret. (`set_thread_dataset` likewise requires a non-empty dataset.)

### Thread Network diagnostics

- **New command `get_thread_diagnostics`.** Args: optional `ext_pan_id` (single network) and `force` (bypass cache).
  - With `ext_pan_id`: awaits a collection and returns the `ThreadDiagnosticsBatch`, or `null` when nothing is cached / diagnostics are disabled.
  - Without `ext_pan_id`: returns the **current cache** for all known networks (an array, possibly empty) **immediately**, and kicks off a background refresh (honoring `force`) whose fresh batches arrive via `thread_diagnostics_updated`. It does not wait for the refresh — use the `ext_pan_id` form when you need synchronously-fresh data for one network.
- **New event `thread_diagnostics_updated`** → a `ThreadDiagnosticsBatch`, emitted as batches stream in from Border Routers. **Delivered only to connections that have issued a Thread request** (`get_thread_diagnostics` or `get_thread_border_routers`) during their lifetime. This gates the schema-12 event away from older (schema-11) clients — which would disconnect on an unknown event type — until they opt in by requesting Thread data. A client that never uses the Thread API never receives it.
- **`get_thread_border_routers`** entries gained mDNS-sourced fields (software/record version, border-agent id).

See `packages/ws-client/src/models/model.ts` for the exact `ThreadDiagnosticsBatch` /
`ThreadDiagnosticsNode` / `BorderRouterEntry` wire shapes (each field is documented inline,
with the schema version that introduced it).

### Fabric label

- **New command `get_fabric_label`** → `{ fabric_label: string | null }` — returns the currently configured fabric label so clients can read it instead of assuming their own value. Counterpart to `set_default_fabric_label`.
- **`set_default_fabric_label` may be ignored.** When the server is started with `--default-fabric-label` (env `DEFAULT_FABRIC_LABEL`), the label is pinned: `set_default_fabric_label` is accepted but does nothing (the server logs the ignored value and keeps the pinned one). Read the effective value with `get_fabric_label`.
- **`set_default_fabric_label` is owned per connection.** Independent of the CLI pin, the first connection to issue `set_default_fabric_label` in a server session owns the label while it stays connected; other connections' set requests are accepted but ignored (and logged) until the owner disconnects. Ownership then passes to the next connection that issues the command.

### WebRTC camera live view

The WebRTC command + event first shipped under schema 11 (PR #644) without being documented or
gated; schema 12 is where they're formally specified, so treat WebRTC as a schema-12 capability
(`server_info.schema_version >= 12`).

- **Command `send_webrtc_provider_command`** (client→server) — relays a `ProvideOffer` / `SolicitOffer`
  to a camera endpoint's WebRTC provider.
- **Event `webrtc_callback`** (server→client) — `offer` / `answer` / `ice_candidates` / `end` for an
  active session (payload `WebRtcCallbackData`). An `offer`'s `ice_servers` use the same
  `{ urls, username?, credential?, caid? }` shape `camera_start_stream` takes, with `urls` a list. **Delivered only to connections that have issued a
  `send_webrtc_provider_command`** during their lifetime — the callbacks reach the client driving that
  camera session, not every connection. **Outgoing events carry no `require_schema`**: that mechanism
  gates client *requests*, not server-emitted events — clients detect support via
  `server_info.schema_version`.
